# Requirements Document

## Introduction

`skeleton-ui` is the package `skeleton/ui` (`@alidade/ui`). It holds everything both apps need to put a sighting on screen: the camera image, the geometry that turns a tap on the image into a direction, the sighting session that goes from a sensor source to one capture, the plain-language messages, the reticle and readouts, the map that draws bearings and fixes with their uncertainty, the panel that drives the Simulator on a laptop, and a playground page that wires them together. It depends on `@alidade/sensors` and `@alidade/core` and on nothing else in the repository (`structure.md`). The browser sensor APIs stay in `@alidade/sensors`; the camera image (`getUserMedia`) and React live here.

The package has three layers, in the way `skeleton-sensors` separates its Math layer from its Adapters:

- the **Math layer**: pure functions and the pure sighting-session state machine: image geometry, ray uncertainty, session transitions and readouts, map geometry, scene projection, messages, display formatting. It reads no clock and no randomness and touches no browser API, no React and no map library, and it is covered by property tests;
- the **Components layer**: React components and the code that binds them to a Sensor source with an injected Clock and Timer. It touches the DOM only through React. It is covered by example tests against fakes and the Simulator source, in a simulated DOM;
- the **Adapters**: two thin modules over browser or third-party APIs, the Camera adapter (`getUserMedia`) and the Map adapter (MapLibre GL JS). Each takes the API as an injected object, so that its tests use a fake and no real browser, camera or map is involved.

All conventions in `.kiro/steering/math-conventions.md` are binding, including the findings of the sensor probe of 2026-11-15. Two of them shape this package. The camera's field of view is not reported reliably by the browser, so it is a calibration with an uncertainty that the caller passes in, and nothing defaults it. And the open item of the probe (camera altitude 3.3° low on iOS, cause not established) means that the package must not hide the difference between "the crosshair" and "the point the user tapped".

Product principles bind this package directly: a fix is never drawn without its 95 % ellipse (principle 1, Requirement 15); the limits of the phone are stated, with the uncertainty of every result shown beside it (principle 2, Requirement 13); and every sensor-driven screen runs from the Simulator (principle 4, Requirements 16 to 18).

New dependencies, all pinned to exact versions that the design fixes after checking the registry (Requirement 20): `react` and `react-dom` (the UI library `tech.md` prescribes), `maplibre-gl` (the map library `tech.md` prescribes), `vite` (the build tool of `tech.md`, for the Playground), for the tests a simulated DOM and a component test library, because a component cannot be rendered without a DOM and the tests may not use a real browser, and, at the repository root, `eslint-plugin-react-hooks`. Each is justified in Requirement 20.

Out of scope: the solver's measurement models and the solver itself (the Playground calls Core's `solve`, but no function of this package does); anything only one app needs (satellite hotspots, wind, ephemerides, the Sun's position, automatic detection of the Sun's glare, sharing sightings between phones); a procedure to measure the camera's field of view; landscape layouts; native apps; accounts; and languages other than English.

The private folder `notes/` holds real locations and is not read or copied. Every scene, landmark, station and fixture of this package is synthetic (Requirement 17.1).

## Glossary

- **UI**: the `@alidade/ui` package specified here. **Sensors** and **Core** are the packages `@alidade/sensors` and `@alidade/core`. **Result**, **Reason**, **Bearing observation**, **Position**, **Supported position**, **Fix**, **Ellipse** and **Local plane** are as defined in the sighting-core requirements. **Sensor source**, **Simulator source**, **Orientation sample**, **Frame reset**, **Sample history**, **Sighting window**, **Yaw reference**, **Declination**, **Ray offset**, **Off-axis ray**, **Camera axis**, **Screen angle**, **Altitude calibration**, **Clock**, **Spread**, **North reference**, **Absolute frame** and **Relative frame** are as defined in the skeleton-sensors requirements.
- **Math layer**, **Components layer**, **Camera adapter**, **Map adapter**: the layers of the Introduction. An **Adapter** is the Camera adapter or the Map adapter.
- **UI reason**: a member of the closed set of Requirement 2.2: every Reason of Sensors plus the reasons added here. **UI result**: a Result whose failure carries a UI reason.
- **CSS pixel**: the unit of the layout of the page, `px` in CSS, named with the suffix `Px` (Open question 1). **Source pixel**: a pixel of the image the camera delivers, named with the suffix `SourcePx`.
- **Pixel point**: `{ xPx, yPx }` in CSS pixels, relative to the top left corner of an element, `xPx` to the right and `yPx` downward. **Pixel size**: `{ widthPx, heightPx }`.
- **Source image**: the image the camera delivers, as it is displayed upright in the portrait screen, with its size in source pixels. **Element**: the rectangle of the page in which the image is displayed.
- **Image fit**: how the Source image is scaled into the Element, always preserving its aspect ratio and centred: `cover` (scaled until it fills the Element, the excess cropped, CSS `object-fit: cover`) or `contain` (scaled until it fits inside the Element, leaving bars, CSS `object-fit: contain`).
- **Image layout**: the plain record of how a Source image of a given size sits in an Element of a given size under an Image fit: the scale in CSS pixels per source pixel, the displayed size and the position of the displayed image in the Element.
- **Camera calibration**: `{ fovRad, fovAxis, fovSigmaRad, imageWidthSourcePx, imageHeightSourcePx }`: the field of view of the pinhole camera along `fovAxis` (`width`, `height` or `diagonal` of the Source image), its 1-sigma, and the size of the Source image it was measured with. It defines the focal length in source pixels `f = (D / 2) / tan(fovRad / 2)`, where `D` is the width, the height or the diagonal of the Source image, and the principal point at the centre of the Source image.
- **True pose**: the camera direction (azimuth, apparent altitude and roll) that the Simulator's script gives at the current simulated time, or that `aim` last set, before noise, bias and frame are applied (Sensors Requirement 12.9). **Aim**: to replace the script's pose with one the reviewer chose (Sensors Requirement 12.10; Requirement 17.10).
- **Image angular sigma**: the 1-sigma, in radians, of the angular error of a direction taken from a point of the image (Requirement 6).
- **Mark**: the Ray offset, with its Image angular sigma, that the user chose by tapping the frozen image. A capture without a Mark uses the Camera axis.
- **Sighting session** (**Session**): the state, in plain data, of one sighting from the first permission to one capture, and the pure function `step` that advances it. **Session state**: one of `permission`, `starting`, `live`, `frozen`, `captured`, `failed`. **Session event**: plain data given to `step`. **Session parameters**: every number and limit the Session uses, passed in (Requirement 19). **Notice**: a failure the Session records without changing its Session state.
- **Session driver**: the code of the Components layer that subscribes to a Sensor source, turns what it delivers into Session events with the time of the source's Clock, and runs the effects the Session asks for. It holds no browser API.
- **Live readout**: the numbers shown while the Session is live: the azimuth with its North reference, the apparent altitude, the Spread and the steadiness. **Readout interval**: the least time between two publications of the Live readout. **Steadiness**: `steady`, `settling` or `unsteady`, from the Spread and two thresholds.
- **Freeze**: the transition from `live` to `frozen`. **Frozen history**: the Sample history at the moment of the Freeze, which later samples never change. **Frozen window**: the Sighting window that ends at the time of the Freeze.
- **Yaw status**: `none`, `valid`, `stale` or `invalidated`, with the age of the Yaw reference (Requirement 11).
- **Message**: `{ whatHappened, whatToDo }`, two sentences in English for the user, for one UI reason.
- **Tile source**: the data that names where map tiles come from (Requirement 15.2). **Fix layer**: the one map layer that draws a Fix and its ellipse.
- **Wedge**: the polygon from an observer's Position that spans the observer's bearing line's azimuth ± 1 sigma out to the line's length.
- **Synthetic scene**: plain data that describes an invented place, its Stations and its Targets (Requirement 16). **Station**: a Position of the observer in a scene. **Target**: a landmark, or the Sun, in a scene. **Scene image**: the drawing of a Synthetic scene that replaces the camera image.
- **Timer**: `{ start(callback, intervalMs): handle, stop(handle) }`, injected wherever the package waits. **Simulator panel**: the component of Requirement 17. **Playground**: the page of Requirement 18.
- **Default parameters**: the named constants of Requirement 19.

## Requirements

### Requirement 1: Package boundaries and layering

**User Story:** As the skeleton's maintainer, I want the browser, the camera and the map confined to thin modules, so that the logic can be tested everywhere and the apps depend on one stable surface.

#### Acceptance Criteria

1. THE UI SHALL depend at runtime on `@alidade/core`, `@alidade/sensors`, `react`, `react-dom` and `maplibre-gl`, and on no other package, and SHALL import Sensors and Core only through their `src/index.ts`. THE UI SHALL NOT import from `apps/*`.
2. THE Math layer SHALL NOT import React, `react-dom`, `maplibre-gl` (not even its types) or any browser global, SHALL NOT read the clock, generate random numbers or perform I/O, and SHALL receive every time, every seed and every size as an argument. A test SHALL run the Math layer's tests in a Node environment with no DOM and SHALL scan its imports.
3. THE UI SHALL NOT reference `DeviceOrientationEvent`, `navigator.geolocation`, `navigator.permissions`, `screen.orientation` or `visibilitychange` anywhere; only Sensors touches them (`tech.md`). A test SHALL scan the package's source for these names.
4. THE Camera adapter alone SHALL reference `navigator.mediaDevices`, `MediaStream` and `MediaStreamTrack`; THE Map adapter alone SHALL import `maplibre-gl`, and only inside one loader module through a dynamic `import()`, so that importing the package's `src/index.ts` in a test environment does not load `maplibre-gl`.
5. THE Components layer SHALL read time only from the Clock of a Sensor source and SHALL wait only through an injected Timer; no module of the package SHALL call `Date.now`, `performance.now`, `setTimeout` or `setInterval` directly except the one module that provides the default Timer of the Playground.
6. THE UI SHALL pass plain data (numbers, strings, booleans, `null`, plain objects and arrays of them) between its layers, apart from the DOM and map objects that an Adapter or a component holds privately.
7. THE UI SHALL export its public API only from `src/index.ts`, its `package.json` exports map SHALL expose only `"."`, and neither the Playground nor test support code SHALL be exported.
8. THE UI SHALL build and pass its tests under TypeScript `strict` mode with no use of `any`, and the Math layer SHALL contain no non-null assertion.
9. THE UI SHALL name every duration with the suffix `Ms`, every time instant with `UtcMs`, every angle in radians with `Rad`, every length in metres with `M`, CSS pixels with `Px` and source pixels with `SourcePx`.
10. THE UI SHALL convert between radians and degrees, and format and parse angles for display, in one module of the Math layer (Requirement 3.8), using Core's `degToRad` and `radToDeg`; no other module SHALL contain a conversion factor between degrees and radians or a value named `Deg`, and a literal in degrees SHALL appear only as the argument of that module's conversion function, except the GeoJSON boundary of Requirement 14.1.

### Requirement 2: Failures and reasons

**User Story:** As an app developer, I want every way the screen can fail to arrive as a value with a closed set of reasons, so that a refused camera or a bad tap never crashes the page and never goes unexplained.

#### Acceptance Criteria

1. THE UI SHALL NOT throw, and SHALL NOT return or store `NaN` or an infinite number, for any input that passes type checking, in any function of the Math layer, any Adapter and any Session event. A caught exception from a browser or library object SHALL become a failure value.
2. THE UI SHALL define a closed set of failure reasons, `UiReason`, exported with its list `UI_REASONS`: every `SensorReason` of Sensors (which includes every Reason of Core), unchanged in meaning, and these added by the UI: `camera_permission_denied`, `camera_unavailable`, `camera_busy`, `camera_track_ended`, `camera_stopped`, `camera_failed`, `wrong_camera`, `calibration_missing`, `calibration_mismatch`, `outside_image`, `outside_field_of_view`, `portrait_required`, `action_not_available`, `tiles_unavailable`, `map_unavailable`, `crosses_antimeridian`. Neither Core nor Sensors SHALL be changed for them.
3. THE UI SHALL return failures as `{ ok: false, reason, field?, id?, reportedAccuracyM?, errorName? }`, where `field` names the offending input, `id` the offending observation, `reportedAccuracyM` is carried through from Sensors' `coarse_location`, and `errorName` is the `name` of a browser error that an Adapter mapped, kept for developers and never shown to the user.
4. IF an input number is `NaN`, infinite or outside its stated range, THEN the function SHALL return a failure with reason `invalid_number` naming the field; a failure from Sensors or Core SHALL be passed through with its reason and fields unchanged.
5. THE UI SHALL NOT drop a failure it receives: each failure given to a Session event, to an Adapter callback or to a component SHALL appear in the Session's `failure` or Notice, in the value an Adapter returns, or on the screen through Requirement 3.
6. FOR ALL values of type-correct inputs drawn by each public Math layer function's generator, including `NaN`, `±Infinity`, `-0`, negative sizes and values at the limits, the function SHALL return without throwing, and every number reachable in its result SHALL be finite.

### Requirement 3: Messages and display

**User Story:** As a volunteer firefighter or a student in the field, I want every failure explained in plain words with what to do next, so that a raw code never appears on my screen and a refusal never leaves me guessing.

#### Acceptance Criteria

1. THE UI SHALL provide one function, `messageFor(failure)`, that returns a Message for every UI reason, built from one table keyed by UI reason. Each Message SHALL have a `whatHappened` that says what went wrong in plain English and a `whatToDo` that says what the user can do next.
2. THE table SHALL be complete: its type SHALL be `Record<UiReason, …>`, so that adding a reason without a Message fails type checking, and a test SHALL check at run time that `UI_REASONS` lists exactly the keys of the table, that the set equals the union of the reasons of Sensors, of Core and of Requirement 2.2, and that no reason has an empty part.
3. EACH part of a Message SHALL be one sentence of at most 160 characters, ending with a full stop, that contains none of: the reason's code, an underscore, `NaN`, `Infinity`, `undefined`, `null` or `[object`. A Message SHALL NOT depend on the `field`, `id` or `errorName` of the failure: the Message of a failure SHALL equal the Message of the same failure without them.
4. WHERE a reason has a number that helps the user (`coarse_location` with `reportedAccuracyM`), THE Message SHALL include it, rounded to the nearest 10 m below 1000 m and to 0.1 km from 1000 m, and SHALL NOT include it when it is missing, `NaN` or infinite.
5. THE Message SHALL be a pure function of the failure: the same failure SHALL give the same Message, in English only.
6. THE Components layer SHALL show every failure it shows through `messageFor`, and SHALL NOT show `reason`, `field` or `errorName` to the user.
7. THE Message of each camera reason, of `permission_denied`, `permission_required`, `insecure_context`, `sensor_unavailable`, `portrait_required`, `compass_unreliable`, `frame_reset`, `stale_yaw_reference`, `coarse_location` and `declination_unknown` SHALL name the thing the user can act on (the camera, motion access, the page address, the phone's orientation, the compass, the sighting of north, the location) and SHALL NOT say only "try again".
8. THE display module SHALL provide a function that formats an azimuth in degrees with a given number of decimals, in `[0°, 360°)`, and one for an altitude or a signed angle in `[-180°, 180°]`; it SHALL provide a function that parses a number of degrees typed by the user into radians, returning `invalid_number` for text that is not one finite number.
9. FOR ALL azimuths in `[0, 2π)` rad and decimals in `[0, 4]`, the formatted azimuth SHALL be a number in `[0, 360)` (never `360.0`) and SHALL differ from the azimuth in degrees by at most `0.5 · 10^-decimals + 1e-9`, compared as a wrapped difference.
10. FOR ALL signed angles in `[-π, π]` rad and decimals in `[0, 4]`, the formatted text SHALL parse back to within `0.5 · 10^-decimals + 1e-9` degrees of the angle, and SHALL NOT be `-0` or begin with a minus sign when it rounds to zero.
11. FOR ALL failures, built from every UI reason with `field`, `id` and `errorName` strings of 0 to 40 arbitrary characters and `reportedAccuracyM` any number including `NaN` and `Infinity`, `messageFor` SHALL return Messages that satisfy criterion 3.

### Requirement 4: Camera calibration

**User Story:** As a developer, I want the camera's field of view passed in with its uncertainty and never assumed, so that a bearing taken off the crosshair is never more accurate than the phone's lens is known to be.

#### Acceptance Criteria

1. THE UI SHALL validate a Camera calibration and return it, or a failure with reason `invalid_number` naming the first invalid field, when `fovRad` is not in `(0, π)`, `fovAxis` is not `width`, `height` or `diagonal`, `fovSigmaRad` is not finite or is below `0.01°` (the least 1-sigma Core accepts for an azimuth), `fovRad - fovSigmaRad` is not above `0` or `fovRad + fovSigmaRad` is not below `π`, or a size of the Source image is not finite and positive.
2. THE UI SHALL NOT define a default Camera calibration, a default field of view or a default `fovSigmaRad`, and no function SHALL accept a missing one as "unknown, assume a value". WHERE a function needs a Camera calibration and receives none, it SHALL return a failure with reason `calibration_missing`.
3. THE UI SHALL compute the focal length in source pixels `f = (D / 2) / tan(fovRad / 2)`, with `D` the width, the height or the diagonal `hypot(width, height)` of the Source image the calibration states. This is the focal length at the calibration's own image size; the geometry of Requirement 5 applies the field of view to the image as displayed.
4. IF the aspect ratio of the actual Source image differs from that of the calibration's image size by more than `1 %` (relative), THEN every use of the calibration with it SHALL return a failure with reason `calibration_mismatch`, because the browser has cropped the image differently from the way the field of view was measured.
5. THE UI SHALL treat the Source image's width and height as those of the image displayed upright in the portrait screen; IF the stream delivers them swapped, THEN criterion 4 applies and refuses it rather than correcting it.
6. FOR ALL Source image sizes in `[64, 8192]` source pixels per side, and `fovRad` in `[20°, 150°]` with `fovSigmaRad` in `[0.01°, 5°]` that satisfy criterion 1, the calibration SHALL be accepted; for each of the invalid cases of criterion 1, a failure naming the right field SHALL be returned.
7. FOR ALL Source image sizes and Camera calibrations as in criterion 6 with `fovAxis` `diagonal`, the calibration with `fovAxis` `width` and `fovRad' = 2 · atan((width / diagonal) · tan(fovRad / 2))` (with any `fovSigmaRad` that is valid for it, since the focal length does not depend on it) SHALL give the same focal length within a relative `1e-12`, and likewise for `height`.

### Requirement 5: Image layout and image geometry

**User Story:** As a Vigia user, I want a tap on the frozen image to give the true direction of what I tapped, whatever the screen size and however the browser crops the image, so that my bearing points at the smoke and not at the crosshair.

#### Acceptance Criteria

1. THE Math layer SHALL compute the Image layout of a Source image of size `(sw, sh)` in an Element of size `(ew, eh)` under an Image fit as: scale `s = max(ew / sw, eh / sh)` for `cover` and `min(ew / sw, eh / sh)` for `contain`, displayed size `(sw · s, sh · s)`, centred in the Element, so that the centre of the Source image is at `(ew / 2, eh / 2)`. IF a size is `NaN`, infinite or not positive, THEN it SHALL return `invalid_number` naming the field.
2. THE Math layer SHALL turn a Pixel point `(x, y)` of the Element into a Ray offset of Sensors as `rightRad = atan((x - ew / 2) / F)` and `upRad = atan(-(y - eh / 2) / F)`, with `F = (Dd / 2) / tan(fovRad / 2)` the focal length in CSS pixels, where `Dd` is the width, the height or the diagonal of the displayed image along `fovAxis` (the field of view is an angle, so it is applied to the image as displayed; the calibration's own image size serves only the aspect check of Requirement 4.4; a pinhole camera whose optical axis passes through the centre of the Source image, with no lens distortion); `yPx` grows downward and `upRad` upward.
3. THE Math layer SHALL turn a Ray offset into a Pixel point by the inverse, `x = ew / 2 + F · tan(rightRad)` and `y = eh / 2 - F · tan(upRad)`, and report with it whether the point lies inside the Element and whether it lies on the displayed image.
4. THE checks of a Pixel point SHALL run in this order and return the first failure: `invalid_number` for a number that is not finite; `calibration_mismatch` (Requirement 4.4); `outside_image` when the point lies outside the Element or, under `contain`, on a bar, with a tolerance of `1e-9` CSS pixels; `outside_field_of_view` when `|rightRad|` or `|upRad|` exceeds `MAX_RAY_OFFSET_RAD` of Sensors.
5. IF a Ray offset given to the inverse is `NaN`, infinite or beyond `MAX_RAY_OFFSET_RAD`, THEN it SHALL return `invalid_number` naming `rightRad` or `upRad`, as Sensors does.
6. THE Math layer SHALL NOT read the Screen angle: the offset is in the device frame, which is the screen's frame only when the Screen angle is `0` (Requirement 10.2 refuses a Mark otherwise).
7. FOR ALL Elements and Source images with sides in `[64, 4096]` CSS pixels and `[64, 8192]` source pixels, both Image fits, all Camera calibrations of Requirement 4.6 whose image size has the aspect ratio of the Source image, and all Pixel points on the displayed image whose offset is within `±79°`, converting to a Ray offset and back SHALL return the Pixel point within `1e-9` CSS pixels.
8. FOR ALL the same layouts and calibrations and all Ray offsets in `[-80°, 80°]`, converting to a Pixel point and back (the point not being required to lie in the Element) SHALL return the Ray offset within `1e-9` rad.
9. FOR ALL the same layouts and calibrations, the centre of the Element SHALL give the Ray offset `(0, 0)` within `1e-12` rad.
10. FOR ALL the same layouts, calibrations and points, a point to the right of the centre SHALL give `rightRad > 0` and one below it `upRad < 0`, and the point mirrored about the centre SHALL give the negated offset, within `1e-9` rad (the mirrored point is rounded to the floating-point grid at the Element's size, and a short focal length magnifies that rounding).
11. FOR ALL the same layouts and calibrations and all factors `k` in `[0.25, 4]`, multiplying the Element, the Pixel point and the displayed scale by `k` SHALL leave the Ray offset unchanged within `1e-9` rad.
12. FOR ALL Elements and Source images as in criterion 7, the Image layout under `cover` SHALL cover the Element (displayed width ≥ `ew` and displayed height ≥ `eh`, within `1e-9`), under `contain` SHALL lie inside it, and under both SHALL have the aspect ratio of the Source image within a relative `1e-12` and be centred within `1e-9` CSS pixels.
13. FOR ALL Elements, Source images and calibrations as in criterion 7 under `contain`, the Pixel point at the left (or right) edge of the displayed image, on the horizontal centre line, SHALL give `|rightRad| = fovRad / 2` within `1e-9` rad when `fovAxis` is `width`, the point at the top (or bottom) edge on the vertical centre line SHALL give `|upRad| = fovRad / 2` when it is `height`, and the corner of the displayed image SHALL give an angle from the Camera axis of `fovRad / 2` when it is `diagonal`, the angle being that of the Off-axis ray of Sensors at an identity rotation.
14. FOR ALL layouts, calibrations and Pixel points on the image with offsets within `±79°`, the angle between the Off-axis ray (at any Device rotation) and the Camera axis SHALL equal `atan(r / F)` within `1e-9` rad, where `r` is the distance of the point from the centre in CSS pixels.
15. FOR ALL layouts and calibrations of criterion 7, a Pixel point inside the Element SHALL be accepted if and only if both `|rightRad|` and `|upRad|` are within `MAX_RAY_OFFSET_RAD` and, under `contain`, the point is on the displayed image; generators SHALL draw points at least `1e-6` rad from the limit, and the limits SHALL have example tests of their own.
16. WHEN given the same inputs, THE Math layer SHALL return the same outputs.

### Requirement 6: Uncertainty of a point of the image

**User Story:** As a Nonius user, I want a sight taken off the crosshair to carry the uncertainty of the lens and of my finger, so that tapping the edge of the image never looks as accurate as aiming the centre.

#### Acceptance Criteria

1. THE Math layer SHALL compute the Image angular sigma of a Pixel point as `hypot(εTap, εFov)`, where `εTap = tapSigmaPx / hypot(r, F)` with `tapSigmaPx` the 1-sigma of the tap in CSS pixels passed in by the caller, and `εFov` is the larger of `|atan(r / F⁺) - atan(r / F)|` and `|atan(r / F⁻) - atan(r / F)|`, where `F⁺` and `F⁻` are the focal lengths in CSS pixels of the calibration with `fovRad ± fovSigmaRad`.
2. THE UI SHALL NOT define a default for `tapSigmaPx`; it is a required finite number of at least `0`, and a failure with reason `invalid_number` naming it SHALL be returned otherwise.
3. THE Image angular sigma SHALL be returned with the Mark, so that Requirement 12 combines it with the sigma of the capture and the screen can show it.
4. FOR ALL layouts, calibrations as in Requirement 5.7 and Pixel points on the image, with `tapSigmaPx` in `[0, 50]`, the Image angular sigma SHALL be finite, SHALL be at least `εTap`, and SHALL equal `εTap` within `1e-12` rad at the centre of the Element.
5. FOR ALL the same layouts, calibrations and Pixel points with offsets within `±75°` (so that the same pixel under `fovRad + fovSigmaRad` stays inside the `80°` that Sensors accepts), the angle between the Off-axis rays (Sensors, identity rotation) of the same Pixel point under `fovRad` and under `fovRad + fovSigmaRad`, and under `fovRad - fovSigmaRad`, SHALL NOT exceed the Image angular sigma by more than `1e-9` rad.
6. THE Math layer SHALL have an example test of `εTap` at the centre of a known layout: for `tapSigmaPx = 1` and `F = 500` CSS pixels, `εTap = 1 / 500` rad within `1e-12`.

### Requirement 7: Camera adapter

**User Story:** As an app developer, I want the rear camera started and stopped by my code and every way it fails delivered as a value, so that a refused permission or a camera taken by another app is a message and not a blank page.

#### Acceptance Criteria

1. THE Camera adapter SHALL take its browser surface as an injected object (the secure-context flag, `getUserMedia`, and the track and stream operations it needs), SHALL read no global, and SHALL start the camera only when the caller calls `start`, never on creation, so that iOS can be asked from a user gesture.
2. IF the page is not a secure context, THEN `start` SHALL return a failure with reason `insecure_context` before calling any camera API; IF the surface has no `getUserMedia`, a failure with reason `camera_unavailable`.
3. THE Camera adapter SHALL request video only (no audio), with `facingMode` `{ ideal: 'environment' }` and, when the caller passes them in, the ideal width and height (the size of the calibration's image when the caller has a calibration, so that the browser's crop matches it; none when it has not, Requirement 18.3), and SHALL NOT use `facingMode` `exact`.
4. THE Camera adapter SHALL map the failure of `getUserMedia` by the `name` of the error, and keep the name in `errorName`: `NotAllowedError` and `SecurityError` to `camera_permission_denied`; `NotFoundError` and `OverconstrainedError` to `camera_unavailable`; `NotReadableError` and `AbortError` to `camera_busy`; any other name, any rejection that is not an error object, and any exception thrown by the surface, to `camera_failed`.
5. IF the started track reports `facingMode` `user`, THEN `start` SHALL stop it and return a failure with reason `wrong_camera`, because the geometry of Requirement 5 is that of the rear camera; IF it reports no `facingMode`, THE Camera adapter SHALL accept it and mark the stream `facing: 'unknown'`; it SHALL mark one that reports `environment` `facing: 'rear'`.
6. THE Camera adapter SHALL return, on success, a stream handle with the Source image size from the track's settings, `facing`, an `onEnded` subscription, and `stop`, and SHALL report the Source image size again, through a subscription, when the video reports different dimensions after it starts playing.
7. WHEN a started track ends (the `ended` event), THE Camera adapter SHALL deliver a failure with reason `camera_track_ended` to every `onEnded` listener, once, and SHALL stop the other tracks of the stream.
8. WHEN the caller calls `stop`, THE Camera adapter SHALL stop every track, remove every listener it added and release the stream; a second `stop` SHALL do nothing. IF `stop` is called while `start` is pending, THEN the pending `start` SHALL settle with a failure with reason `camera_stopped`, and a stream that arrives afterwards SHALL be stopped at once.
9. WHEN `start` is called while a start is pending or the camera is running, THE Camera adapter SHALL NOT call `getUserMedia` a second time; the call SHALL settle with the same result as the first.
10. THE Camera adapter SHALL NOT throw, SHALL NOT leave a track running on any failure path, and SHALL hand the rest of the package no browser object other than the stream handle's private reference that the video component attaches.
11. THE Camera adapter SHALL be covered by example tests against a fake surface for each reason of criteria 2, 4, 5, 7 and 8, for the success path, for criterion 9 and for the cleanup of criterion 10 (no fake track left running).

### Requirement 8: Sighting session: states and transitions

**User Story:** As an app developer, I want one pure state machine for the path from permission to a capture, so that both apps behave the same and every path can be tested without a phone.

#### Acceptance Criteria

1. THE Session SHALL be plain, immutable data, and `step(state, event, parameters)` SHALL be a pure function that returns a new Session (or the same state with a Notice) and the effects it asks for, as plain data. `step` SHALL NOT change its arguments, read the clock or wait.
2. THE Session events SHALL be: the result of the orientation permission request, the result of starting orientation, an Orientation sample or a failure, a Frame reset, a Position fix or a failure, a Declination or a failure, the state of the camera (running, or a failure), `tick`, `freeze`, `unfreeze`, `mark` (a Pixel point with the layout and calibration), `clearMark`, `capture`, `establishYaw`, `again` and `restart`. Every event SHALL carry `timeUtcMs` from the source's Clock.
3. THE Session SHALL begin in `permission`. The transitions SHALL be exactly these:
   - `permission`, a granted or not-required permission → `starting`, and the effect "start orientation"; a failure → `failed`.
   - `starting`, orientation started → `live`; a failure → `failed`.
   - `live`, a successful `freeze` → `frozen` (Requirement 10.1).
   - `frozen`, `unfreeze` → `live`; a successful `capture` → `captured`.
   - `captured`, `again` → `live`.
   - `failed`, `restart` → `permission`, keeping the Yaw reference, the Declination and the Frame resets and dropping the Orientation samples (criterion 14).
   - any state but `captured` and `failed`, a camera failure → `failed` with that failure; in `captured`, a camera failure SHALL be a Notice and the result SHALL be kept.
4. THE Session events SHALL be of two kinds: action events, which the user causes (`freeze`, `unfreeze`, `mark`, `clearMark`, `capture`, `establishYaw`, `again`, `restart`), and data events, which arrive (all the others). An action event in a state that does not offer it SHALL leave the Session unchanged except for a Notice with reason `action_not_available`. A data event SHALL never give `action_not_available`: one that carries a failure and fits no transition SHALL record that failure's own reason as the Notice, in every Session of either kind, and one that carries no failure and fits no transition SHALL be dropped. No event SHALL throw.
5. IN `live`, a failed Orientation sample (for example `sensor_unavailable` for an event with a `null` angle) SHALL become a Notice and SHALL NOT change the state; the Session SHALL leave `live` for `failed` only through the transitions of criterion 3.
6. THE Session SHALL keep the Sample history of Sensors for the live samples in every state from `starting` on, and in `frozen` SHALL go on adding live samples to it while the Frozen history stays as it was (Requirement 10.3).
7. A failure the Session records SHALL be kept in `failure` (when the state is `failed`) or in the Notice (otherwise), with its reason and `field` unchanged, its `reportedAccuracyM` unchanged when it is a finite number and left out when it is not (criterion 8), and the time of the event. A Notice SHALL be replaced by the next Notice and cleared by the next action event or state transition that succeeds. A sample, Frame reset, Position fix, Declination or `tick` that succeeds SHALL neither set nor clear a Notice, so that a Notice is not wiped by the samples that arrive many times a second.
8. THE Session SHALL carry no `NaN` or infinite number, and a Session event with one in a time or a measurement SHALL produce a Notice with reason `invalid_number`, or the failure of Sensors' history functions, and SHALL leave the rest of the Session unchanged.
9. FOR ALL sequences of 0 to 200 events drawn from the Session events with valid and invalid payloads (including failures of every reason, times that do not increase and values `NaN` and `Infinity`), `step` SHALL NOT throw, and the Session after every event SHALL contain only finite numbers.
10. FOR ALL sequences as in criterion 9, every consecutive pair of Session states SHALL be a pair of criterion 3 or a pair of the same state.
11. FOR ALL sequences as in criterion 9 run twice, and on states that are deeply frozen before each `step`, the results SHALL be equal and `step` SHALL NOT have modified its arguments.
12. FOR ALL sequences as in criterion 9, every failure carried by a data event SHALL appear, with its reason, in the `failure` or the Notice of the Session returned by that same `step`.
13. THE Session SHALL be created for one kind of capture, `bearing` or `altitude`. A bearing Session SHALL ask for the effect "start positions" when it enters `starting`; an altitude Session SHALL never ask for it and SHALL never ask for a Declination, so that an application that needs no position never requests one (Sensors Requirement 7.1).
14. THE Session SHALL add every Frame reset it receives to its Sample history in every Session state, `permission` and `failed` included, and `restart` SHALL keep the Frame resets, so that a reset received while the Session was not live still invalidates the Yaw reference the Session keeps (Requirement 11.9).
15. IF a `sample`, `frameReset` or `positionFix` event carries an item whose own `timeUtcMs` is later than the `timeUtcMs` of the event that carries it, THEN the Session SHALL refuse it with a Notice with reason `invalid_number` naming `timeUtcMs` and SHALL leave its history unchanged. The Session driver stamps the event from the same Clock the source stamped the item with, after the item, so a real event never does this. Without this rule one item with a time far in the future would make the Sample history drop every real Frame reset and every real sample (Sensors Requirement 14.2 keeps items relative to the newest time), and a Yaw reference the phone has lost would read `valid` again (Requirement 11.9).
16. THE Session's time SHALL be the largest event time it has seen, and THE Session SHALL handle every event at the Session's time: an event whose `timeUtcMs` is earlier than the Session's time (the clock stepped back) SHALL be handled as if it carried the Session's time. This handled time is the end of the Sighting window of a `freeze`, of an `establishYaw` and of the Live readout, the time of the staleness checks, the time of a capture and the time recorded with a failure; wherever these requirements say "the event's time" for one of those, they mean it. The items an event carries keep their own times (criterion 15 compares an item's time with the time the event itself carries). So the Session never reads a window that ends before a Frame reset it has already accepted: while the clock is behind the Session's time, a `freeze` or an `establishYaw` fails with Sensors' own reasons (`frame_reset`, `stale_samples` or `insufficient_samples`) until the clock has caught up. Without this rule, a clock that steps back just after a Frame reset (a phone correcting its clock when it wakes) would let a window that ends before the reset's time pass Sensors' check, and the Session would sight against a north the phone has lost.

### Requirement 9: Session driver and Live readout

**User Story:** As a user outdoors, I want numbers I can read, updated a few times a second and not at the sensor's rate, so that the digits do not blur while I aim.

#### Acceptance Criteria

1. THE Live readout SHALL hold: the azimuth with its North reference (`true`, `magnetic` or `relative`), the apparent altitude, the Spread of the azimuths and the standard deviation of the altitudes over the last Sighting window, the Steadiness, the number of samples, the time of the newest sample, and `stale` when the newest sample is older than the sample staleness limit at the time of the last `tick`.
2. THE Live readout's azimuth SHALL be computed as the circular mean of the azimuths of the samples in the window, each given the North reference by Sensors' rules and no stronger one: a Relative-frame sample with a valid Yaw reference (Requirement 11) through it, and `relative` without one; an Absolute-frame sample through the Yaw reference when it is valid, and `magnetic` otherwise; and then `true` only when a Declination is held and the North reference is `magnetic`. THE Live readout SHALL NOT label an azimuth `true` that Sensors would not return as true.
3. THE Live readout's apparent altitude SHALL be the mean of the altitudes of the samples in the window plus the `offsetRad` of the Altitude calibration the caller passes in.
4. THE Steadiness SHALL be `steady` when the Spread is at most `steadyBelowRad`, `unsteady` when it is above `unsteadyAboveRad`, and `settling` otherwise, with both thresholds passed in as parameters (Requirement 19).
5. THE Session SHALL publish a new Live readout only when at least the Readout interval has passed since the last publication, measured with the events' `timeUtcMs`, and SHALL otherwise keep the previous one; every Orientation sample SHALL be added to the Sample history whether or not a Live readout is published.
6. IF the window holds no sample, THEN the Live readout SHALL be `null`, not zeros.
7. THE Session driver SHALL subscribe to the Sensor source's three subscriptions, turn each delivery into a Session event stamped with `source.now()`, call `tick` through the injected Timer at the Readout interval, run the effects of the Session (request permission, start orientation, start positions, compute the Declination with Sensors' `declinationAt` on each new Position fix), and unsubscribe from everything and stop its Timer when it is stopped.
8. WHEN the driver is stopped, THE Session driver SHALL remove every listener and timer it added, as Sensors does (Sensors Requirement 11.9), and SHALL start no second subscription when started again while running.
9. FOR ALL Sample histories (generated as in Sensors Requirement 14.6), Yaw references, Declinations and windows whose samples are all in one frame and none lacks a way to north, the Live readout's azimuth SHALL equal the azimuth of the Bearing that Sensors' `captureBearing` returns for the same window (no Ray offset, a valid Position fix) within `1e-9` rad as a wrapped difference, and its apparent altitude SHALL equal that of `captureAltitude` for the same calibration within `1e-12` rad.
10. FOR ALL sequences of 0 to 500 Orientation samples with increasing times and all Readout intervals in `[50, 2000]` ms, the number of Live readouts published SHALL be at most `floor(span / interval) + 1`, any two published `timeUtcMs` SHALL differ by at least the interval, and the Sample history SHALL equal the one built by adding every sample with Sensors' functions.
11. FOR ALL azimuth sets within `30°` of a common direction and all rotations `δ` in `[0, 2π)`, adding `δ` to every azimuth SHALL add `δ` to the Live readout's azimuth within `1e-9` rad (wrapped difference) and SHALL leave the Spread and the Steadiness unchanged within `1e-12` rad.
12. THE Session driver SHALL be covered by example tests against the Simulator source and an injected Timer: permission denied, permission required, sensor missing, insecure context, a start that settles, a restart, and the unsubscription of criterion 8.

### Requirement 10: Freeze and mark

**User Story:** As a Vigia user, I want to freeze the image and then tap the smoke calmly, so that my hand's shake while aiming does not enter the bearing.

#### Acceptance Criteria

1. THE `freeze` event SHALL succeed in `live` only if the Sighting window ending at its time holds at least the minimum number of samples and its newest sample is not stale at that time (Sensors' rules); otherwise it SHALL leave the Session `live` with a Notice with reason `insufficient_samples` or `stale_samples`.
2. THE `freeze` event SHALL succeed, and `mark` SHALL be accepted, only when the Screen angle of the newest sample in the window is `0` within `1e-9` rad; IF it is another angle or `null`, THEN they SHALL leave the state unchanged with a Notice with reason `portrait_required`. Every capture goes through a Freeze, so the package works in portrait only (Open question 7).
3. WHEN the Session freezes, THE Session SHALL keep the Sample history of that moment as the Frozen history, including its Frame resets and its latest Position fix, the Frozen window (ending at the event's `timeUtcMs`, with the Sighting window length of the parameters), and the Yaw reference and Declination held at that moment; and nothing that arrives afterwards SHALL change them. The one exception is the user's own `establishYaw` in `frozen` (Requirement 11.1), which replaces the Yaw reference of the Frozen sighting and nothing else.
4. WHEN the Session is `frozen`, THE image component SHALL show the frame that was on screen at the Freeze and SHALL keep showing it, at the same Element and Image fit, until `unfreeze` or `again` (Device check 4).
5. A `mark` event SHALL carry a Pixel point, the Image layout and the Camera calibration, SHALL be turned into a Mark by Requirements 5 and 6, and SHALL replace any earlier Mark; IF it fails, THEN the earlier Mark SHALL stay and the failure SHALL be a Notice with its reason (`outside_image`, `outside_field_of_view`, `calibration_missing`, `calibration_mismatch` or `invalid_number`).
6. THE Session SHALL keep the Mark as the Ray offset and its Image angular sigma, not as a Pixel point, so that a change of the Element's size (a rotation of the page, a keyboard) does not move the Mark; the screen SHALL draw it again from the offset (Requirement 13.3). `clearMark` SHALL remove it.
7. WHEN the Session leaves `frozen` (by `unfreeze`, `again` or a failure), THE Session SHALL drop the Frozen history and the Mark.
8. FOR ALL event sequences that reach `frozen`, and all samples and Frame resets delivered afterwards with any times, the Frozen history, the Frozen window and the capture produced from them SHALL equal exactly those produced when no later event is delivered.
9. FOR ALL Sample histories that allow a freeze (generated as in Sensors Requirement 14.6 with at least the minimum number of fresh samples in the window and Screen angle `0`), the Frozen history SHALL equal the Session's history at the time of the event (same samples, same Frame resets, same Position fix).
10. FOR ALL Pixel points and layouts of Requirement 5.7 whose offsets are within `±79°`, a Mark's offset SHALL equal the offset of Requirement 5.2 within `1e-12` rad, and after `mark` with a point that fails, the Mark SHALL equal the Mark before.

### Requirement 11: Yaw reference in the session

**User Story:** As an iPhone user, I want to see where the app's north came from, how old it is, and when a lock screen or a page switch has made it unsafe, so that I never sight against a north the phone has lost.

#### Acceptance Criteria

1. THE Session SHALL hold at most one Yaw reference, set only by an `establishYaw` event: from the compass, through Sensors' `yawReferenceFromCompass`, or from a known azimuth (a Sun or landmark the caller computed), through `yawReferenceFromKnownAzimuth`, over the Sighting window ending at the event's time, with the samples and Frame resets of the Session's history. A failure of Sensors SHALL be passed through as a Notice with its reason, and the Yaw reference held before SHALL stay. `establishYaw` from the compass SHALL be offered in `live` only. `establishYaw` from a known azimuth SHALL be offered in `live`, on the Camera axis, and in `frozen`, over the Frozen history and the Frozen window with the Mark's Ray offset when there is one, so that the user can freeze, mark the Sun or a landmark calmly and then give its azimuth; with a Mark, the 1-sigma given to Sensors SHALL be `hypot(σ, ε / cos(h))`, with `σ` the 1-sigma of the known azimuth and `ε` and `h` as in Requirement 12.3.
2. THE UI SHALL NOT establish a Yaw reference without an `establishYaw` event. A Relative-frame Session with no valid Yaw reference SHALL report Yaw status `none` and its Live readout SHALL carry the North reference `relative` (Open question 5).
3. THE UI SHALL provide a pure function `yawStatus(yawReference, frameResets, nowUtcMs, maxAgeMs)` that returns `none` when there is no Yaw reference; `invalidated` when a Frame reset that invalidates it under Sensors Requirement 5.17 lies in the closed interval from the time it was established to `nowUtcMs`; `stale` when its age exceeds `maxAgeMs`; otherwise `valid`; and always its age in milliseconds, which is never negative. `invalidated` SHALL take precedence over `stale`.
4. THE screen SHALL show the Yaw status with the age (for example "north set 42 s ago") and the North reference and 1-sigma of the Yaw reference, and SHALL show a prompt to establish it again when the status is `invalidated` or `stale`, with the wording of the Message for `frame_reset` or `stale_yaw_reference`. WHEN the Yaw status is `none`: in a Session whose samples are in the Relative frame, the screen SHALL show the prompt with the wording of the Message for `no_yaw_reference`; in a Session whose samples are in the Absolute frame, the phone's own compass gives north (Requirement 9.2), so the screen SHALL NOT say that north is not set: it SHALL state that north comes from the phone's compass, with the heading 1-sigma of the parameters in degrees, and that setting north on the Sun or a landmark reduces the error.
5. THE Session SHALL NOT discard an invalidated or stale Yaw reference; it SHALL pass it on as it is to the capture, so that Sensors returns `frame_reset` or `stale_yaw_reference` rather than a bearing against a lost north (Sensors Requirement 5.18).
6. IF the Screen angle of the newest sample is not `0` or is `null`, THEN `establishYaw` from the compass SHALL return the failure of Sensors, `compass_unreliable`, and the screen SHALL show the Message of `portrait_required` beside it.
7. FOR ALL Sample histories (as in Sensors Requirement 14.6) with Frame resets of any cause, Yaw references of either frame, times and maximum ages in `[1000, 150 000]` ms, a capture window ending at `nowUtcMs` that holds enough fresh samples of the Yaw reference's frame, and a Yaw reference established no later than the window's start (a Session cannot produce the other case, because establishing north over a window that holds such a reset fails; it has an example test): `yawStatus` `valid` SHALL hold if and only if Sensors' `captureBearing` on that window with that Yaw reference does not fail with `frame_reset` or `stale_yaw_reference`; `invalidated` if and only if it fails with `frame_reset`; and `stale` only if it fails with `stale_yaw_reference`.
8. FOR ALL Yaw references and times, `yawStatus`'s age SHALL equal `nowUtcMs - establishedUtcMs` when that is not negative and `0` otherwise.
9. FOR ALL sequences of Session events as in Requirement 8.9 (their times do not have to increase) in which a Yaw reference is established and the Session afterwards accepts a Frame reset that invalidates it under Sensors Requirement 5.17 (its cause invalidates the reference's frame and its time is not earlier than the time the reference was established), in any Session state and with any events between and after, `restart` included: from the event that delivers the reset, and for as long as the Session holds that Yaw reference, or another of the same frame established no later than the reset's time (one established in `frozen` over a Frozen window from before the reset), (a) the Yaw status SHALL never be `valid`; and (b) no bearing capture SHALL succeed with such a Yaw reference for a sighting frozen after that event. A sighting frozen before the reset was delivered is made of samples taken before it, against the north the phone still had; its capture is the one of Requirement 10.8 and is not changed by the reset. The property SHALL count every such reset the Session accepted, whether or not the history still holds it, and SHALL report how many it saw in each Session state and how many captures it saw refused under (b). This is the property that the Session never sights against a north the phone has lost; it rests on Requirements 8.14, 8.15, 8.16 and 19.4.

### Requirement 12: Capture

**User Story:** As a Nonius user, I want a captured altitude to carry the lens and tap uncertainty on top of the sensor's, so that a sight taken at the edge of the image never claims the accuracy of one taken at the crosshair.

#### Acceptance Criteria

1. THE `capture` event in `frozen` SHALL, for a bearing Session, call Sensors' `captureBearing`, and for an altitude Session `captureAltitude`, with the Frozen history's samples, Frame resets and Position fix, the Frozen window, the Mark's Ray offset when there is one, and the Yaw reference, Declination, calibration and limits held by the Session or its parameters; a failure of Sensors SHALL be passed through as a Notice, and the Session SHALL stay `frozen`.
2. IF a bearing capture has no Position fix in the Frozen history, THEN `capture` SHALL return a failure with reason `position_unavailable`.
3. WHEN there is a Mark, THE capture of a bearing SHALL replace the Bearing's `azimuthSigmaRad` with `hypot(σ, ε / cos(h))`, where `σ` is Sensors' sigma, `ε` the Mark's Image angular sigma and `h` the apparent altitude of the Off-axis ray of the newest sample in the Frozen window (Sensors' `rayDirection` and `directionApparentAltitudeRad`); IF `|h|` is above `80°` it SHALL return `axis_vertical`; and it SHALL validate the result with Core's `validateBearing`, returning `too_unsteady` when the sigma exceeds `45°`.
4. WHEN there is a Mark, THE capture of an altitude SHALL report the sigma `hypot(σ, ε)`, where `σ` is the sigma of Sensors' altitude capture; the apparent altitude SHALL be unchanged.
5. WHEN there is no Mark, THE capture SHALL equal exactly the capture of Sensors with the Camera axis, with no sigma added (Open question 8).
6. THE captured result SHALL carry the Bearing or the altitude capture, and with it the Mark (or `null`), the Yaw reference and the Declination used (or `null`) with their 1-sigmas, the Camera calibration used (or `null`), the number of samples, the Frozen window, and the Spread of the azimuths (for a bearing) or the standard deviation of the altitudes (for an altitude) over that window as Sensors summarises them for that capture, with the Mark's Ray offset when there is one, so that the screen can show what the uncertainty is made of (Requirement 13.5).
7. THE captured result SHALL NOT carry a number that is `NaN` or infinite, and a Bearing SHALL pass Core's `validateBearing`.
8. FOR ALL Frozen histories and Marks of Requirement 10.9 and 10.10 for which the capture succeeds, the captured azimuth (or altitude) SHALL equal that of Sensors called with the Mark's Ray offset within `1e-12` rad as a wrapped difference, the sigma SHALL equal the formula of criterion 3 (or 4) within `1e-12` rad, and, with no Mark, the result SHALL equal Sensors' deeply.
9. FOR ALL Frozen histories, delivering any further samples, Frame resets, positions and Declinations before `capture` SHALL leave the captured result unchanged.
10. FOR ALL Marks with calibrations of Requirement 4.6, the sigma of a capture with a Mark SHALL be at least the sigma Sensors gives for the same capture with the Mark's Ray offset: the Image angular sigma never lowers it. It is not compared with the capture on the Camera axis, because the azimuth of an off-axis ray has a different Spread over the window and its sigma can be either larger or smaller.

### Requirement 13: Reticle, readouts and touch targets

1. THE Reticle SHALL be drawn at the centre of the Element, which is the Camera axis (Requirement 5.9), as two tones: a light core line of at least `2` CSS pixels over a dark outline of at least `1` CSS pixel on each side, with a clear gap at its centre of at least `8` CSS pixels in diameter so that the target is not hidden. It SHALL stay visible on any background of the image.

THE Components layer SHALL define a palette of colour tokens, and the pairs of text or line colour and backing colour it uses, and SHALL give every readout text and every control label a contrast ratio of at least `7 : 1` against its opaque backing (WCAG AAA), computed by a pure function of the Math layer from the WCAG definition of relative luminance.

THE readouts SHALL use a font size of at least `20` CSS pixels, tabular digits, and the formatting of Requirement 3.8; each azimuth SHALL be followed by the word for its North reference (`true`, `magnetic` or `relative`), and a `relative` azimuth SHALL NOT be shown without that word. THE Live readout SHALL show the Spread and the altitudes' standard deviation as the steadiness of the hand, with a label that says so (for example "shake ±0.3°"), and never as a bare `±` beside the azimuth or the altitude: the Spread is not the azimuth's uncertainty, which also holds the north reference, the Declination and the lens, and which the screen shows with a capture (criterion 5).

THE screen SHALL show, with each captured result, its 1-sigma and, in words and with each part's own 1-sigma in degrees, what the uncertainty is made of: the sensor's spread (the Spread or standard deviation the captured result carries), the north reference (the Yaw reference's 1-sigma when one is used, with whether it came from the compass or from a known azimuth; otherwise the heading 1-sigma of the parameters, for the phone's own compass), the Declination, and the lens and tap (the Mark's Image angular sigma as it enters the result), leaving a part out only when the capture does not use it (Requirement 12.6); and a limits line that states that phone compasses are off by several degrees and that calibrating on the Sun or a landmark reduces it.

9. WHEN the Screen angle of the newest sample is not `0` or is `null`, THE screen SHALL show the Message of `portrait_required`.
10. FOR ALL colours of 8-bit sRGB, the contrast ratio SHALL be symmetric in its two arguments, lie in `[1, 21]`, equal `1` for equal colours within `1e-12`, and equal `21` within `1e-9` for black and white.

12. THE component tests SHALL check criteria 1, 3 and 7 through the inline style values and attributes that the components set, because a simulated DOM does no layout; the sunlight and reach parts are Device check 7.

### Requirement 14: Map geometry

**User Story:** As a dispatcher, I want bearings drawn as lines with their uncertainty and a fix drawn with its 95 % ellipse, from plain functions I can test, so that what the map shows is what the solver computed.

#### Acceptance Criteria

1. THE Math layer SHALL build every GeoJSON object the map draws, with coordinates in the order `[lonDeg, latDeg]`, converted from `{ latRad, lonRad }` with Core's `radToDeg`; this is the only place in the package where that order appears.
2. THE Math layer SHALL provide `observerFeatures(observers)`: one Point feature per observer, with the properties `kind: 'observer'` and `id`.
3. THE Math layer SHALL provide `bearingFeatures(bearing, lineLengthM, arcStepRad)`: a LineString from the observer to the Position at `lineLengthM` along the azimuth (Core's `destinationPosition`), and the Wedge polygon of azimuth ± `azimuthSigmaRad`, whose ring starts and ends at the observer's Position and whose other vertices lie on an arc at `lineLengthM`, spaced by at most `arcStepRad` in azimuth and including both edges. `lineLengthM` SHALL be required, finite and in `(0, 500 000]` m, and `arcStepRad` finite and positive; a failure with reason `invalid_number` naming it SHALL be returned otherwise.
4. THE Math layer SHALL provide `fixFeatures(fix, vertexCount)`, which takes a Core Fix (a Fix always has its covariance and its Ellipse) and returns one feature collection with exactly one Point at the Fix's Position (`kind: 'fix'`) and exactly one Polygon (`kind: 'fix-ellipse-95'`) built from `ellipse95(fix.ellipse)` of Core, never from the 1-sigma ellipse, with `vertexCount` at least `16` (default `ELLIPSE_VERTEX_COUNT`, Requirement 19). The vertices SHALL be at the parameters `θk = 2πk / vertexCount` of the ellipse, mapped to East-North metres with the major axis at the Ellipse's azimuth and back to Positions with Core's `unprojectToLocalPlane` about the Fix's Position, in counter-clockwise order, and the ring SHALL be closed.
5. IF `ellipse95` fails or a vertex cannot be unprojected, THEN `fixFeatures` SHALL return the failure and no feature at all, so that the Point of a Fix is never returned without its ellipse; and its type SHALL make a Point-only collection of a Fix impossible to build.
6. THE Math layer SHALL provide `mapBounds(featureCollections)`, which returns the smallest west, south, east, north box (in degrees) that contains every coordinate of the features, and a failure with reason `crosses_antimeridian` when the coordinates do not fit in a box that spans at most `180°` of longitude without crossing `±180°`, or `invalid_number` when there are no coordinates.
7. EVERY feature SHALL carry the `kind` and the `id` of what it draws, and every collection SHALL be plain JSON: serialising it and parsing the text SHALL give an equal value.
8. FOR ALL Bearings with observers at latitudes in `[-84°, 84°]`, azimuths in `[0, 2π)`, sigmas in `[0.01°, 45°]`, lengths in `[100, 500 000]` m (the range in which Core guarantees both round trips, Core Requirements 2.4 and 2.5; shorter lengths have example tests) and arc steps in `[0.1°, 5°]`, the end of the LineString SHALL lie at `lineLengthM` from the observer within `1e-4` m (Core's `greatCircleDistanceM`) and at the Bearing's azimuth within `1e-9` rad (Core's `initialAzimuthRad`, wrapped difference); and every arc vertex of the Wedge SHALL lie at `lineLengthM` within the same tolerance, with azimuth within `[azimuth - sigma, azimuth + sigma]` extended by `1e-9` rad, the first and last arc vertices at the two edges within `1e-9` rad, and consecutive arc vertices no more than `arcStepRad + 2e-9` rad apart in azimuth (a difference of two azimuths, each known within `1e-9` rad).
9. FOR ALL Fixes with semi-axes in `[1, 100 000]` m (`semiMajorM ≥ semiMinorM`), Ellipse azimuths in `[0, π)`, Positions as in Requirement 14.8, and vertex counts in `[16, 360]`, every vertex of the ellipse polygon, projected to the Local plane of the Fix's Position (Core's `projectToLocalPlane`) and expressed in the ellipse's axes, SHALL satisfy `(u / a)² + (v / b)² = 1` within `1e-9 + 2e-4 / b`, where `a` and `b` are the 95 % semi-axes of `ellipse95` in metres and `u`, `v` the coordinates along the major and minor axes (Core guarantees the Local plane's round trip to `1e-4` m, Core Requirement 3.3, and that error is divided by `b`).
10. FOR ALL Fixes as in criterion 9, the ring SHALL be closed exactly (first vertex equal to last), have counter-clockwise orientation in the Local plane, have the mean of its distinct vertices at the Fix's Position within `1e-4 m + 1e-9 · a` in the Local plane, hold the first vertex on the major axis at distance `a` within `1e-4 m + 1e-9 · a`, and the ratio of `a` to the 1-sigma semi-major axis SHALL be `2.4477` within `1e-9` (the literal of math-conventions, not Core's constant).
11. FOR ALL Fixes as in criterion 9, the midpoint of each edge of the polygon, in the ellipse's axes, SHALL satisfy `(u / a)² + (v / b)² = cos²(π / vertexCount)` within `1e-9 + 2e-4 / b`, so that the polygon deviates from the ellipse by at most the sag of a regular polygon.
12. FOR ALL Fixes with an Ellipse that makes `ellipse95` fail (a semi-axis `0`, negative, `NaN` or infinite, or `semiMinorM > semiMajorM`), `fixFeatures` SHALL return a failure and no Point.
13. FOR ALL non-empty sets of features built from Bearings and Fixes as in criteria 8 and 9 within `500 km` of each other, whose longitudes lie within `(-170°, 170°)`, every coordinate SHALL lie inside the box of `mapBounds`, and for sets that straddle `±180°` it SHALL return `crosses_antimeridian`.
14. THE Math layer SHALL provide an example test of each function at a published or hand-computed case with synthetic positions: a bearing due north (`azimuth 0`) from a point at the equator, and a circular Fix of 1-sigma radius `10 m` that gives a polygon of radius `24.477 m` within `1e-4` m.

### Requirement 15: Map adapter

**User Story:** As a Vigia user, I want the map to open from a link with no key in the code, and to show a fix only ever with its ellipse, so that nobody reads a confident dot where there is only a region.

#### Acceptance Criteria

1. THE Map adapter SHALL take the map library as an injected object (a constructor and the few operations it uses, as a minimal interface), SHALL create the map in a container passed in, and SHALL return a failure with reason `map_unavailable` when the library reports that it cannot start (for example no WebGL), never an exception.
2. THE Tile source SHALL be a parameter: `{ tileUrlTemplates: string[], attribution: string, minZoom, maxZoom, tileSizePx }`, or `null` for none. THE Map adapter SHALL return `invalid_number` naming `tileUrlTemplates` when a template lacks `{z}`, `{x}` or `{y}` or the list is empty, and naming `attribution` when it is empty; it SHALL show the attribution on the map. No Tile source, URL or API key SHALL be written in the package; an app reads them from environment variables documented in `.env.example` (`tech.md`).
3. WITH no Tile source, THE Map adapter SHALL draw its features on a plain background with no network request, and SHALL work offline.
4. THE map style SHALL contain no text layer and need no glyph or sprite URL, so that it makes no request other than for tiles; the style SHALL be built by a pure function that returns plain JSON.
5. THE Map adapter SHALL expose `setObservers`, `setBearings(bearings, lineLengthM)`, `setFix(fix)`, `clearFix`, `fitToFeatures(paddingPx)`, `onError` and `destroy`. `setFix` SHALL take a Core `Fix`, and the Map adapter SHALL have no operation that draws a Position as a fix without a Fix.
6. THE Map adapter SHALL write a Fix to the Fix layer in one update of one data source, from the single result of `fixFeatures`, so that a Point and its ellipse change together; IF `fixFeatures` fails, THEN `setFix` SHALL clear any Fix drawn before (its Point and its ellipse together), change nothing else on the map, and return the failure: a Fix that could not be drawn must not leave an older one on the screen as if it were current.
7. THE Map adapter SHALL order its layers so that the ellipse is drawn under the Point and the Wedges under the lines, and SHALL draw lines and outlines at least `2` CSS pixels wide with the contrast of Requirement 13.2 against a light and against a dark background (the two-tone construction of the Reticle).
8. WHEN a tile fails to load, or the map library reports a source error, THE Map adapter SHALL deliver a failure with reason `tiles_unavailable` to its `onError` listeners, at most once per second, and SHALL keep drawing its features.
9. THE Map adapter SHALL NOT add a geolocation control or call any browser sensor API, and SHALL make no request except for tiles.
10. WHEN the caller calls `destroy`, THE Map adapter SHALL remove the map and every listener it added; a later call of any operation SHALL return a failure with reason `action_not_available`, not throw.
11. FOR ALL sequences of 0 to 100 calls of `setObservers`, `setBearings`, `setFix`, `clearFix` and `fitToFeatures`, with valid and invalid arguments, on a fake map: the Fix layer's data SHALL contain a Point if and only if it contains exactly one ellipse Polygon; it SHALL contain at most one Point; after `clearFix` or a failed `setFix` it SHALL be empty; and after a successful `setFix(f)` it SHALL equal `fixFeatures(f)` deeply.
12. FOR ALL such sequences, the map's data after the sequence SHALL equal the data built from the last arguments given to each operation, so that the order of earlier calls does not matter.
13. THE Map adapter SHALL be covered by example tests against a fake of the library for criteria 1 to 10, with no real map and no WebGL; the fake SHALL record the data it is given.
14. THE Map adapter SHALL let an application draw layers of its own beside the skeleton's, through one general operation, `setLayer(id, collection, paint)`, and `clearLayer(id)` (both apps need it: Vigia for the sightings it has set aside and for its overlays, Nonius for its lines of position). `id` SHALL be a string of 1 to 32 characters, a lower-case letter followed by lower-case letters, digits or hyphens, and SHALL NOT be one of the skeleton's own source ids. `collection` SHALL be a feature collection of the Math layer whose features each carry a `kind` and an `id` (Requirement 14.7). `paint` SHALL be plain data of a closed form: a `kind` of `fill`, `line` or `circle`, a colour written `#RRGGBB`, and, where the kind has them, a width or radius in CSS pixels in `(0, 16]`, an opacity in `(0, 1]` and a dash pattern of at most 4 positive numbers. The style SHALL gain no text layer, no sprite and no glyph, and the operation SHALL make no network request. THE Math layer SHALL provide the builder of such features from Positions (a point, a line or a polygon given as Positions, with its `kind` and `id`), so that an application never writes the longitude-latitude order of the map itself (`math-conventions.md`); it SHALL refuse a Position that is not Supported with `unsupported_position` and a line of fewer than 2 or a polygon of fewer than 3 Positions with `invalid_number`, and SHALL close a polygon's ring. `MapView` SHALL take the application's layers as a prop, each with whether the map is fitted to it.
15. `setLayer` SHALL refuse, with `invalid_number` naming the field and with the layer left as it was: an `id` or a `paint` outside criterion 14; more than `MAX_APP_LAYERS` (`8`) layers; a collection of more than `MAX_LAYER_FEATURES` (`2 000`) features; a coordinate that is not finite or not a Supported position; and any feature whose `kind` is one of the skeleton's own (`observer`, `bearing-line`, `bearing-wedge`, `fix`, `fix-ellipse-95`), so that a Fix can still be drawn by `setFix` alone and never without its ellipse (criterion 6, Requirement 13.6). After `destroy` it SHALL fail as the other operations do.
16. THE layers of an application SHALL be drawn under every layer of the skeleton, in the order in which their ids were first set, so that the Wedges, the Bearings, the observers and the Fix with its ellipse are never hidden by them; and `fitToFeatures` SHALL take them into account only when the caller passes their collections.
17. FOR ALL sequences of 0 to 100 calls of `setLayer`, `clearLayer` and the operations of criterion 11, with valid and invalid arguments, on a fake map: the data of each application layer SHALL equal the last collection successfully given to it (or be absent after `clearLayer`); the properties of criteria 11 and 12 SHALL still hold, so that no call of `setLayer` or `clearLayer` changes the Fix, the Bearings or the observers; no application layer SHALL hold a feature of a skeleton `kind`; and the skeleton's layers SHALL stay above every application layer in the style's order.

### Requirement 16: Synthetic scene

**User Story:** As a reviewer on a laptop, I want a drawn scene in place of the camera, projected with the same geometry as the real image, so that tapping a landmark gives its true direction and I can test the whole flow without going outside.

#### Acceptance Criteria

1. THE Math layer SHALL define a Synthetic scene as plain data: an `id`, a name, a Camera calibration (that of the synthetic camera), a list of at least two Stations (an `id`, a name and a Position), and a list of Targets, each either a landmark (an `id`, a label, a Position and a height `heightM` above the observer) or the Sun (an `id`, a label, a true azimuth, an apparent altitude and an angular radius), and SHALL validate it, returning `invalid_number` naming the field or `unsupported_position` for a Position that is not a Supported position.
2. THE Math layer SHALL compute the true direction of a Target from a Station: for a landmark, the true azimuth from Core's `initialAzimuthRad` and the apparent altitude `atan2(heightM, distanceM)` with `distanceM` from `greatCircleDistanceM` (a synthetic simplification that ignores the curvature of the Earth and refraction, stated in the scene's documentation); for the Sun, its given direction. A Target at a distance under `1` m SHALL be refused with `coincident_positions`.
3. THE Math layer SHALL provide `projectScene(scene, station, trueRotation, layout)`, which takes the true Device rotation of the simulated camera, read from the Simulator's controls (Sensors Requirement 12.12), and the Image layout, and returns, for each Target, its Pixel point, whether it is visible (in front of the camera, within `MAX_RAY_OFFSET_RAD`, inside the Element and on the image: under `contain` the bars beside the image are not part of it, so that every visible Target can be tapped and marked, Requirement 5), and for the Sun its radius in CSS pixels `F · tan(angularRadius)`; and the horizon as the line (two Pixel points clipped to the part of the Element that the image covers, or `null` when the horizon is not in view there). The horizon SHALL be built so that it is found at every pose of criterion 7: from the horizon point at the camera's own azimuth, whose angle from the Camera axis is the camera's altitude and which Sensors' inverse can therefore always place, the line being perpendicular to the segment from the image centre to that point; near a level camera, where that segment is too short to give a direction, from two horizon points beside the camera's azimuth.
4. THE projection SHALL use the geometry of Requirement 5 and Sensors' own inverse of the Off-axis ray (Sensors Requirement 3.10), and the UI SHALL contain no rotation matrix of its own, so that the Scene image and the Orientation samples of the Simulator source come from the same truth.
5. THE Scene image SHALL be drawn by a component that takes the result of `projectScene` and the Image layout, and that is used by the screen in place of the camera image through the same interface, so that the Session, the Reticle and the Mark cannot tell it from the camera image.
6. THE Scene image SHALL draw the horizon, each visible Target with its label, and the Sun as a disc, and SHALL show no text that gives a Target's direction (the Simulator panel shows the true directions, Requirement 17.7).
7. FOR ALL Synthetic scenes with Stations and Targets at least `1` m apart, true poses with azimuths in `[0, 2π)`, apparent altitudes in `[-80°, 80°]` and rolls in `[-π, π)`, layouts as in Requirement 5.7 and Targets that `projectScene` reports visible, taking the Pixel point through Requirement 5.2 and the Off-axis ray of Sensors at the Device rotation of the Orientation sample that a Simulator source with no noise, no altitude bias, an Absolute frame with no north error and Declination `0` delivers for that true pose SHALL give the true direction of the Target within `1e-9` rad of angle.
8. FOR ALL scripts of the Simulator with noise `0`, an altitude bias `0`, an Absolute frame with north error `0`, or a Relative frame whose compass heading includes the scripted Declination and a Yaw reference established from the compass, a constant pose, at least the minimum number of samples in the Frozen window, and Targets that are visible: running the Session through `freeze`, `mark` (at the Target's Pixel point) and `capture` SHALL give a Bearing whose azimuth equals the Target's true azimuth within `1e-8` rad as a wrapped difference, and an altitude capture whose apparent altitude equals the Target's within `1e-8` rad. This is the property that tapping a landmark gives its true direction.
9. FOR ALL poses and layouts as in criterion 7, every point of the horizon (apparent altitude `0`, any true azimuth) that `projectScene` reports visible SHALL lie on the horizon line within `1e-6` CSS pixels, and a Target behind the camera SHALL be reported not visible.
10. FOR ALL Targets and Stations, the true direction of criterion 2 SHALL be finite, with the azimuth in `[0, 2π)` and the altitude in `[-π/2, π/2]`.
11. THE Math layer SHALL provide an example test of criterion 2 for a landmark `1000 m` due east and `100 m` high from a synthetic Station: azimuth `π/2` within `1e-9` rad and altitude `atan(0.1)` within `1e-12` rad.

### Requirement 17: Simulator panel

**User Story:** As a reviewer on a laptop, I want to pick a scripted scene and watch it run, so that I can exercise every screen of the app and every failure path with no phone, no camera and no GPS.

#### Acceptance Criteria

1. THE UI SHALL provide a catalogue of Synthetic scenes, each with at least two Stations and its Simulator scripts, built from one synthetic origin Position by offsets in metres on the Local plane (Core's `unprojectToLocalPlane`); the origin, and the reason it implies no real place, SHALL be stated in the catalogue's documentation (Open question 10). No Position, name or value in the catalogue SHALL come from `notes/`.
2. THE catalogue SHALL hold at least these scenes: a steady Absolute-frame phone; a Relative-frame phone with a compass (the iPhone case, with a scripted altitude bias of `-3.3°`); a compass that jumps; a Frame reset between the Yaw reference and the capture; a coarse location; a position that is denied; an orientation permission that is required, and one that is denied; a missing orientation sensor; and a page that is not a secure context. Each scene SHALL give a different Message on screen when its failure is reached.
3. EVERY script of the catalogue SHALL pass the Simulator's own validation, SHALL set a Camera calibration consistent with the Scene image of its scene, and SHALL start with the camera pointed at one Target and hold that pose, so that a reviewer who does not aim can still freeze, mark and capture.
4. THE Simulator panel SHALL let the reviewer choose a scene, a Station, a seed (a non-negative integer, validated), a speed (`0.25×`, `1×` or `4×`) and play, pause, step and restart; and a change of scene, Station or seed SHALL create a new Simulator source (Sensors' `createSimulator`) and a new Session, and stop the old ones.
5. THE Simulator panel SHALL drive the Simulator's clock only through `advanceTo` of the controls, from an injected Timer: each tick SHALL advance the time by `tickMs × speed`, the first advance being from the script's `startUtcMs`; no advance SHALL exceed `MAX_SIMULATOR_ADVANCE_MS` (the function that lists the advances splits a longer one; with the bounds below, a tick or a step is always a single advance); the panel SHALL read no clock; and WHEN paused or stopped it SHALL have no running timer. THE panel's state SHALL be bounded: a tick length of at most `MAX_PANEL_TICK_MS` (`60 000` ms) and an elapsed simulated time of at most `MAX_PANEL_ELAPSED_MS` (ten years). IF a panel state holds a tick length or an elapsed time beyond those limits (or one that is not finite, a tick length that is not positive, an elapsed time that is negative), or IF a tick or a step would take the elapsed time beyond its limit, THEN the panel's step function SHALL return `invalid_number` naming the field and leave the state unchanged; it SHALL NOT throw, loop without end or build a list of advances whose length is not bounded by these limits (Requirement 2.6).
6. IF `advanceTo` or `createSimulator` returns a failure, THEN the panel SHALL pause, show the failure through `messageFor`, and keep its state.
7. THE Simulator panel SHALL show the truth of the scene for the reviewer: the true azimuth and altitude of the camera and the true direction of each Target from the chosen Station, as text; and the Scene image SHALL replace the camera image (Requirement 16.5).
8. FOR ALL speeds, tick lengths in `[10, 1000]` ms and sequences of 0 to 200 actions (play, pause, step, restart, speed changes, ticks), the simulated time the panel has advanced to SHALL never decrease except at a restart, SHALL equal the script's `startUtcMs` plus the sum of `tickMs × speed` of the ticks delivered while playing (and of the steps) within a relative `1e-12`, and SHALL NOT advance while paused.
9. THE Simulator panel SHALL be covered by example tests with a fake Timer and the real Simulator source, for criteria 4 to 7, 10 and 11, and the catalogue by example tests for criteria 2 and 3, one per scene.
10. THE Simulator panel SHALL let the reviewer aim the simulated camera while the Session is not `frozen`, by dragging on the Scene image and by the arrow keys in steps of `1°`, through `aim` of the Simulator's controls (Sensors Requirement 12.10). The new pose SHALL come from a pure function of the Math layer, `aimAfterDrag(pose, dxPx, dyPx, F)`: the azimuth decreases by `atan(dxPx / F) / cos(h)`, with `h` the apparent altitude before the drag, and the apparent altitude increases by `atan(dyPx / F)`, so that the scene follows the pointer at any altitude (to first order, with the roll near `0`); the azimuth is wrapped to `[0, 2π)`, the altitude is limited to `[-80°, 80°]` and the roll is unchanged.
11. WHILE the Session is `frozen`, a tap on the image SHALL be a Mark (Requirement 13.8) and a drag SHALL NOT aim.
12. FOR ALL poses with azimuths in `[0, 2π)`, altitudes in `[-80°, 80°]` and rolls in `[-π, π)`, drags of up to `±4096` CSS pixels on each axis and `F` in `[50, 20 000]` CSS pixels, `aimAfterDrag` SHALL return a finite pose with the azimuth in `[0, 2π)`, the altitude in `[-80°, 80°]` and the roll unchanged; a zero drag SHALL return the pose within `1e-12` rad; a horizontal drag (`dyPx = 0`) followed by the opposite drag SHALL return the azimuth within `1e-9` rad as a wrapped difference; and any drag followed by the opposite drag SHALL return the altitude within `1e-9` rad when neither step reached the limit.
13. THE UI SHALL export what an application needs to build Synthetic scenes of its own (both apps do): `sceneFromOffsets` with its `SceneSpec`, `StationSpec` and `TargetSpec`, and a function `scriptForStation(scene, stationId, aimTargetId, options)` that returns the Simulator script of one Station, starting pointed at one Target and holding that pose, with options for the start time, the orientation noise, the frame (with its north error or its zero) and the other fields the catalogue varies. It SHALL refuse an unknown Station or Target id with `invalid_number` naming the field, a scene that fails `checkScene` with that failure unchanged (`unsupported_position` for a Position, Requirement 16.1), a Target under `1` m away with `coincident_positions`, and an option that is not finite with `invalid_number` naming it. An application's scenes stay in the application: the catalogue of criterion 2 SHALL NOT grow for them.
14. THE catalogue of criterion 2 SHALL be built through `scriptForStation`, and its scenes and scripts SHALL equal, deeply, those it gave before this function existed (a regression example test over all eleven scenes).
15. FOR ALL scenes built by `sceneFromOffsets` from generated offsets (Stations and Targets at least `1` m apart and within `50 km` of the origin, heights within `±5 000` m, and the Sun with any azimuth and an altitude within `±80°`), Stations and Targets of them and valid options, the script of `scriptForStation` SHALL pass the Simulator's own validation, and its first pose SHALL point at the Target from that Station: its azimuth and apparent altitude SHALL equal `targetDirection` within `1e-12` rad (the altitude clamped to the Simulator's `±80°`, with an example test at the clamp).

### Requirement 18: Playground

**User Story:** As a developer, I want a small page that wires the camera, the session, the reticle, the map and the Simulator panel together, so that I can try the flow on a phone and on a laptop before either app exists.

#### Acceptance Criteria

1. THE Playground SHALL be a page inside the package (`skeleton/ui/playground`), built with Vite, started with a package script that is never run by an automated task; it SHALL NOT be part of the public API (Requirement 1.7), and no other module SHALL import it.
2. THE Playground SHALL have two modes, chosen by a visible control: **device** (the Camera adapter and `createBrowserSensorSource`), and **simulator** (the Simulator panel, the Scene image and `createSimulator`). It SHALL start in **simulator** mode when the browser has no `DeviceOrientationEvent` (a feature test, never the user-agent string), and in **device** mode otherwise.
3. THE Playground SHALL ask for the Camera calibration with fields for the field of view in degrees, the axis, and its 1-sigma in degrees, empty at the start, and for the tap's 1-sigma in CSS pixels; it SHALL start the camera and capture on the crosshair without them, and SHALL refuse a Mark with the Message of `calibration_missing` until they are valid (Requirement 4.2, 6.2); the form SHALL also take an optional requested width and height for the camera, and the calibration's image size SHALL be that of the running stream when the calibration is applied; in simulator mode the calibration is that of the scene.
4. THE Playground SHALL show the image (or the Scene image), the Reticle, the Live readout, the Yaw status, the session controls (permission, Freeze, unfreeze, Capture, again, establish north from the compass, establish north from a known azimuth typed in degrees), the failures through `messageFor`, a list of the captures with their sigmas, and a map with the observers, the Bearings with their Wedges and, from two or more Bearings, the Fix that Core's `solve` returns, with its 95 % ellipse (Requirement 15). Beside the list it SHALL show the Fix in words, through a component of the Components layer that takes a Fix (and so cannot be given a position without its Ellipse, Requirement 13.6): the number of Bearings used, the position, and the semi-axes of the 95 % ellipse in metres; or the Message of the failure of `solve`. THE Playground SHALL show the summary of the last capture once, not a second time while the screen itself shows it.
5. THE Playground SHALL read the Tile source from `VITE_TILE_URL_TEMPLATE` and `VITE_TILE_ATTRIBUTION`, documented in `skeleton/ui/.env.example`, and with them absent SHALL show the map on a plain background.
6. THE Playground SHALL include a diagnostics view for the device checks of skeleton-sensors: the orientation event rate in hertz over the last second (Sensors Device check 2); the frame (Absolute or Relative), the Screen angle and the compass heading with its reported accuracy (Device check 3); the Frame resets with their causes and times (Device check 4); and the Yaw reference established from a known azimuth with its age, followed by the difference to a second known azimuth typed in, to show the offset on the Sun or a landmark (Device checks 1 and 5). The view SHALL compute the rate and the differences with the Math layer and show numbers on the screen only.
7. THE Playground SHALL NOT write a file, store data, send data to any server or add an analytics script; the only network requests SHALL be the page's own assets and the tiles of the Tile source. Positions and sightings of a real device SHALL leave the page only by the user selecting and copying them.
8. THE Playground SHALL show failures only through `messageFor`.
9. THE Playground SHALL be covered by an integration example test in the simulated DOM, with the Simulator source, a fake Timer, a fake Camera adapter and a fake map: choose a scene, grant the permission, reach `live`, freeze, mark a Target, capture, change the Station, capture again, and see on the fake map the two observers, two Wedges and one Fix with its ellipse, whose Bearings' azimuths equal the Targets' true azimuths within `1e-8` rad and whose Fix lies within the ellipse of the scene's synthetic target; and the same test with a failing scene (permission denied) that shows its Message. The equality within `1e-8` rad is checked on a copy of the scene with its orientation noise set to `0` and nothing else changed (the catalogue's steady scene has a small noise, so that its sigma is not only the floors); a second test runs the scene as the catalogue has it and checks that the synthetic target lies within the drawn 95 % ellipse.

10. *(Amendment of 2026-11-18.)* THE package SHALL export a component `DeviceSighting` that puts the phone's Sensor source (given by a `createSource` function) and the rear camera (the Camera adapter, given a camera surface) on the sighting screen: ONE tap on Start SHALL ask for the motion permission and start the camera; a Mark without a Camera calibration SHALL show the Message of `calibration_missing` and the crosshair SHALL still capture; a failure of the source or the camera SHALL be shown through `messageFor`; and WHEN the component is unmounted it SHALL stop the camera's tracks (also one that was still starting) and the Sensor source. It SHALL take only what the caller passes in (no global, no Playground state), and the Playground SHALL use it.

### Requirement 19: Default parameters

**User Story:** As an app developer, I want a named default for every tunable limit of the screen, and an explicit parameter in every function, so that I can see in my own code which values I chose.

#### Acceptance Criteria

1. THE UI SHALL export, from one module, these named constants: a Readout interval of `200 ms`; Steadiness thresholds `steadyBelowRad = 0.5°` and `unsteadyAboveRad = 2°` (from the probe's repeatability of the relative frame, `0.3°` to `0.6°`, and of the compass, `0.75°` to `1.7°`); an ellipse vertex count of `72` (`ELLIPSE_VERTEX_COUNT`); a Wedge arc step of `1°`; a minimum touch target of `48` CSS pixels, a primary control height of `64` CSS pixels and a spacing of `8` CSS pixels; a minimum contrast ratio of `7`; a minimum readout font size of `20` CSS pixels; a map error report interval of `1000 ms`; a Simulator tick length of `100 ms`.
2. THE UI SHALL provide the Session parameters as one record built from these constants and from Sensors' defaults (`SIGHTING_WINDOW_LENGTH_MS`, `MIN_SAMPLE_COUNT`, `SAMPLE_STALENESS_MS`, `POSITION_STALENESS_MS`, `COARSE_LOCATION_LIMIT_M`, `YAW_REFERENCE_MAX_AGE_MS`, `HEADING_SIGMA_RAD`, `SAMPLE_RETENTION_MS`, `FRAME_RESET_RETENTION_MS`, `UNCALIBRATED_ALTITUDE`), and each function of the Math layer SHALL take its values as parameters and SHALL NOT read a default implicitly.
3. THE UI SHALL define no default for the Camera calibration or for `tapSigmaPx` (Requirements 4.2 and 6.2), and a test SHALL check that the Session parameters record has no such field.
4. IF a parameter is `NaN`, infinite, not positive where it must be (durations, sizes, steps, vertex counts that are not integers of at least `16`, and the contrast ratio), or an interval is not at least `1 ms`, or the Frame reset retention is less than the Yaw reference maximum age plus the Sighting window length (Sensors Requirement 14.3, on which Requirement 11.9 rests: by Requirements 8.15 and 8.16 the newest time of the history is never later than the Session's time, at which every window ends, so a Frame reset that invalidates a Yaw reference still usable in a window is at most the maximum age before the newest time, and is still held), THEN the function SHALL return a failure with reason `invalid_number` naming the parameter.
5. THE documentation of the Steadiness thresholds SHALL state that they come from the probe on two phones and are to be confirmed by the device checks.

### Requirement 20: Dependencies

**User Story:** As the skeleton's maintainer, I want every new dependency pinned and justified, so that the package stays lean and a build is reproducible.

#### Acceptance Criteria

1. THE `package.json` of the UI SHALL pin every dependency to an exact version (no `^` or `~`), SHALL list `@alidade/core` and `@alidade/sensors` as `workspace:*`, and the design SHALL state, for each dependency, the version chosen after checking the registry.
2. THE UI SHALL add only these, and SHALL justify each in the design: `react` and `react-dom`, the UI library of `tech.md`; `maplibre-gl`, the map library of `tech.md`, used by the Map adapter alone and loaded only through a dynamic import; `@types/react` and `@types/react-dom`, for `strict` type checking of the components; one simulated DOM package for the tests, because no component can be rendered without a DOM and the tests may not use a real browser; `@testing-library/react`, because it renders a component and finds what it shows by role and text, as the user sees it, instead of by the component's internals, with `@testing-library/dom`, the peer it cannot run without; `vite`, the build tool of `tech.md`, for the Playground, with JSX compiled by its built-in transform and no plugin unless the design shows that one is needed; and `eslint-plugin-react-hooks` at the repository root, so that lint refuses a hook called conditionally or a stale dependency list.
3. THE UI SHALL NOT add a state-management library, a CSS framework, a component library, an icon library, a geometry library or a date library, and SHALL NOT add a dependency to do something that takes under 30 lines to write correctly (`tech.md`).
4. THE test tooling already pinned in Sensors (`vitest`, `fast-check`, `vite`, `typescript`) SHALL be used at the same versions.
5. THE UI SHALL read no secret from the repository; the Tile source's URL and attribution are read from environment variables documented in `.env.example`.
6. EVERY version of a dependency this specification adds SHALL have been published at least 14 days before it is installed, and the design SHALL record its publication date, so that a release compromised and withdrawn within days is never installed on the shared machine.

### Requirement 21: Testing split

**User Story:** As the skeleton's maintainer, I want the logic tested by properties and the components and adapters by examples against fakes, so that everything runs on a laptop with no phone and no browser.

#### Acceptance Criteria

1. THE Math layer SHALL be covered by property tests for every FOR ALL criterion of this document, each named with the criterion it validates, with at least `200` cases per property and generators that state their domain (`testing.md`); degenerate cases that a generator excludes SHALL have an example test of their own.
2. THE Components layer SHALL be covered by example tests in a simulated DOM, against the Simulator source, a fake Timer, a fake Camera adapter and a fake map.
3. THE Adapters SHALL be covered by example tests against fakes of `getUserMedia` and of the map library (Requirements 7.11, 15.13), with no real browser, camera, GPU or map.
4. THE example tests of the components SHALL cover each UI reason that a component can show, through `messageFor`, and the Session's every transition of Requirement 8.3, in a table-driven test.
5. A test SHALL fail when a UI reason is added to the closed set and not to the table of Messages (Requirement 3.2), and when a Session transition outside Requirement 8.3 is reachable (Requirement 8.10).
6. THE shrunk counterexample of every property that finds a bug SHALL be kept as an example test (`testing.md`); fixtures are synthetic and read-only.
7. `pnpm test` SHALL run every test once and exit; no task SHALL start a development server or a watch mode (`tech.md`); a deep run with more cases MAY be offered as `test:deep`, as in Sensors.

## Device checks

These behaviours can be confirmed only on a phone. The criteria above do not depend on their being settled, but each one, once measured, may change a default, a limit or a Requirement. They run in the Playground (Requirement 18).

1. **Field of view of each test phone.** Measure the field of view of the iPhone 13 (Safari) and the Xiaomi (Chrome) along each axis, with the stream size the Playground requests, by sighting two targets of known angular separation (for example, the ends of a ruler at a measured distance) and by rotating the phone between them with the gyroscope; record the axis, the value, its repeatability (the `fovSigmaRad`) and the stream size. Check whether the value changes with the requested size, the aspect ratio, a zoom, or the camera chosen (on a phone with several rear cameras, `facingMode: environment` may pick the main, the ultra-wide or another).
2. **How each browser crops and scales the camera image.** Check that the displayed image matches the model of Requirement 5.1 (centred, aspect ratio kept, `cover`): sight one target at the centre and at the edge of the image, and compare the angle between them given by the taps with the angle given by the rotation. Agreement within twice the combined 1-sigma confirms the model. Also check whether iOS applies a stabilisation crop or changes the crop when the stream starts, and whether the stream delivers its dimensions upright in portrait (Requirement 4.5).
3. **Delay between the camera image and the orientation.** Pan the phone quickly across a landmark and measure how far the image lags the orientation samples, to decide whether the Frozen window must end earlier than the time of the Freeze (it ends at the Freeze in this specification).
4. **Holding the frozen image.** Check that pausing the video element keeps the last frame on iOS Safari and on Chrome for Android, and, if either blanks it, that drawing the frame to a canvas at the Freeze does (Requirement 10.4).
5. **Camera facing and the track events.** Read `getSettings().facingMode` on both phones with `facingMode: { ideal: 'environment' }`; check what happens to the track when the app goes to the background, the screen locks, or another app takes the camera (the `ended`, `mute` and `unmute` events, and whether the video freezes silently); decide whether Requirement 7.7 must also treat a muted track as a failure.
6. **The crosshair and the optical axis.** On iOS the camera altitude read `3.3° ± 0.5°` low against the Sun (math-conventions, Open). Sight the Sun's centre by a Mark on the frozen image and by the crosshair, with the glare avoided as far as possible, and compare the altitudes: if the Mark's altitude agrees with the Sun's true altitude and the crosshair's does not, the cause is the crosshair's alignment with the optical axis (Open question 8).
7. **Sunlight and one hand.** Read the Live readout, the Reticle and the map outdoors in full sun on both phones and decide whether a contrast of `7 : 1` and a font of `20` CSS pixels suffice; hold the phone in one hand and check that the controls of Requirement 13.7 can be reached with the thumb.
8. **Tap precision.** Tap the same target of the frozen image 20 times with one hand, and compute the standard deviation in CSS pixels, to choose `tapSigmaPx` for the Playground and the apps.
9. **Screen angle on iOS and Android.** Check that `screen.orientation.angle` is reported on both phones with the page in portrait and after a rotation, and what the page shows when the phone is rotated to landscape (Requirement 13.9, Open question 7).
10. **Rendering and tiles.** Check that MapLibre starts, with its WebGL, on both phones, how long a Fix and its ellipse take to appear, and which Tile source loads from China (Open question 4).

## Open questions

Decisions of the review of 2026-11-18 are recorded with each question. Questions 4, 8 and 13 stay open until their device checks are run.

1. **Suffixes for pixels.** Decided: `Px` (CSS pixels) and `SourcePx` (source pixels) are added to the table of units in `math-conventions.md`.
2. **The true pose of the simulated camera.** Decided: Sensors gains what the UI would otherwise repeat: the true pose, the true Device rotation and `aim` on the Simulator's controls (Sensors Requirements 12.9 to 12.13), the inverse of the Off-axis ray (Sensors Requirements 3.10 and 3.11), and the exports of Sensors Requirement 1.10. The UI SHALL NOT repeat the Simulator's interpolation, a rotation matrix, the selection of a Sighting window, the Spread or the rule of which Frame reset invalidates a Yaw reference.
3. **Detecting the Sun's glare.** Decided: out of this package. The user marks the Sun's glare on the frozen image by hand (Requirement 10); automatic detection is considered again in the Nonius specification.
4. **Tile source.** Open. The package ships none and the Playground reads it from its environment (Requirement 18.5). Which source loads from China is settled by Device check 10; the terms of use of each candidate are read before a demo link is public.
5. **Establishing north.** Decided: only by an explicit `establishYaw` event (Requirement 11.2). The screen prompts for it when the Yaw status is `none`, `invalidated` or `stale`; nothing establishes it silently.
6. **A procedure for the field of view.** Decided: not in this specification. The crosshair works without a calibration (Requirement 18.3); a helper that measures the field of view is considered after Device check 1.
7. **Screen angle `null` and landscape.** Decided: portrait only, and an unknown Screen angle is refused (Requirement 10.2). Reviewed after Device check 9.
8. **Alignment of the crosshair.** Open until Device check 6. No parameter is reserved now.
9. **Aiming in the Simulator panel.** Decided: the reviewer aims by dragging the Scene image or with the arrow keys (Requirement 17.10), through `aim` of the Simulator's controls.
10. **Stations and the synthetic origin.** Decided: every scene has at least two Stations, and the catalogue is built around one invented origin in open sea, `30° N, 40° W`, where no tile shows a real place under the invented landmarks.
11. **React lint rules.** Decided: `eslint-plugin-react-hooks` is added at the root (Requirement 20.2).
12. **The antimeridian.** Decided: refusing a map extent that crosses `±180°` is accepted (Requirement 14.6).
13. **Image and sensor timing.** Open until Device check 3. The Frozen window ends at the Freeze.
