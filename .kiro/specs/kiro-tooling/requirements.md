# Requirements Document

## Introduction

`kiro-tooling` is the last piece of engineering of the entry: the extension points of Kiro itself, used for this repository's own work. Until now the rules in `.kiro/steering/` and in the working rules of the task lists were kept by hand. This specification moves the ones that a program can check into code that Kiro runs, and exposes the skeleton's mathematics to the agent as tools.

Three pieces, all outside `skeleton/` and `apps/`:

- **The guard**, `tools/kiro-guard` (`@alidade/kiro-guard`): one small zero-dependency package of TypeScript with a pure decision function and a command line of five subcommands. It refuses tool calls that break the project's rules, reports the repository's state at the start of a session, reminds the agent of the root checks at the end of a turn, runs a package's tests when a math file is saved, and checks the format of a requirements file.
- **The project agent**, `.kiro/agents/alidade.json`, and **three IDE hooks** in `.kiro/hooks/`, which call the guard.
- **The MCP server**, `tools/alidade-mcp` (`@alidade/mcp`): a stdio server written by hand, without the MCP SDK, with three tools over the skeleton: `fix_from_bearings`, `magnetic_declination`, `local_offset`. It is registered for the workspace in `.kiro/settings/mcp.json` and given to the agent.

Out of scope, as decided by the lead: Powers, a Kiro Crew app, anything that sends data off the machine. Nothing here reads `notes/`. The guard and the server never open a network connection.

## Glossary

- **Guard**: the package `tools/kiro-guard`. **Decision**: its answer for one tool call, `allow`, or `refuse` with a **rule id** and a **reason**.
- **Hook event**: the JSON that Kiro writes to a hook command's standard input: `hook_event_name`, `cwd`, `session_id`, and for tool triggers `tool_name` and `tool_input` (Kiro hooks documentation, "Hook triggers").
- **Repository root**: the folder two levels above `tools/kiro-guard/src`, resolved by the script itself, never taken from the event.
- **Notes folder**: `<repository root>/notes`. **Body keys**: the keys of `tool_input` that hold text to be written or searched for and not a path: `text`, `content`, `file_text`, `oldStr`, `newStr`, `old_str`, `new_str`, `query`, `prompt`. The key `pattern` is not a Body key: its value is examined up to its first glob character (`*`, `?`, `[`, `{`), so that `notes/**` is refused and `**/*.ts` is not.
- **Shell word**, **shell segment**: a word, or a command between `;`, `&&`, `||`, `|`, `&` or a newline, of a shell command after quotes are removed (design §4.2).
- **Dual-era server**: an MCP server that answers both the `initialize` handshake of protocol versions up to `2025-11-25` and the per-request `_meta` of version `2026-07-28` (design §7.1).
- **Tool outcome**: the value a tool handler returns: `{ ok: true, … }` or `{ ok: false, reason, message }`. **Hostile input**: any JSON value, including `1e999` (which `JSON.parse` turns into `Infinity`), `-0`, empty and very long strings, and deeply nested arrays.

## Requirements

### Requirement 1: The guard refuses the tool calls that break the project's rules

**User Story:** As the lead, I want the rules that have been kept by hand to be refused by code, with a reason the agent can act on, so that a tired or mistaken agent cannot read private notes, commit, or leave a server running.

#### Acceptance Criteria

1. THE Guard SHALL export `decide(event: unknown, context: GuardContext): Decision`, a pure function that reads no file, starts no process and reads no clock, where `GuardContext` holds `repositoryRootAbs`, `homeAbs` and an optional `only` list of rule ids. FOR ALL JSON values as `event` and for `context.only` any subset of the rule ids, it SHALL return without throwing a `Decision` whose `reason` contains no `undefined`, `null` or `[object`.
2. THE command `node tools/kiro-guard/src/main.ts pre-tool-use` SHALL read the hook event from standard input and, WHEN the Decision is `allow`, exit `0` with nothing on standard output and standard error; WHEN it is `refuse`, exit `2`, write nothing to standard output and write one line to standard error of the form `kiro-guard: refused [<rule id>] <reason> Instead: <what to do>`. WHEN standard input is not valid JSON, is not an object or is longer than 1 MiB, it SHALL refuse with rule id `bad-input`.
3. THE Guard SHALL refuse exactly these calls, each under its rule id, and no other:

| Rule id              | Refused                                                                                                                                                                                                                    | Still allowed (each is an example test)                                                                                          |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `notes-private`      | any tool call one of whose paths resolves to the Notes folder or below (criterion 4)                                                                                                                                       | `docs/notes/a.md`, `notes.md`, `skeleton/core/notes.ts`, a write whose `text` mentions `notes/`                                  |
| `no-pkill`           | a shell segment whose command is `pkill` or `killall`                                                                                                                                                                      | `kill 123`, `echo pkill`                                                                                                         |
| `no-git-commit`      | a shell segment whose command is `git`, after its global options (`-C <dir>`, `-c <k=v>`, `--git-dir=…`, `--work-tree=…`, `--no-pager`), with subcommand `commit`                                                          | `git status`, `git diff`, `git log -1`, `git add -N .`                                                                           |
| `no-git-push`        | the same with subcommand `push`                                                                                                                                                                                            | `git fetch --dry-run`                                                                                                            |
| `no-dev-server`      | `pnpm [options] dev`, `pnpm [options] run dev`, the same with `preview` or `start`; `vite`, `vite dev`, `vite preview` or `vite serve`, bare or through `pnpm exec`, `pnpm dlx`, `npx`                                     | `pnpm --filter @alidade/nonius build`, `vite build`                                                                              |
| `no-watch-mode`      | `vitest`, bare or through `pnpm exec`, `pnpm dlx`, `npx`, without `run`, `related` or `--run` among its arguments                                                                                                          | `timeout 60 vitest run src/a.test.ts`                                                                                            |
| `install-offline`    | `pnpm add` or `pnpm install` or `pnpm i` without `--offline`; `pnpm install` and `pnpm i` are also allowed with `--frozen-lockfile`                                                                                        | `pnpm add --offline x`, `pnpm install --frozen-lockfile`, `pnpm install --offline`                                               |
| `test-needs-timeout` | a shell segment that runs a test (`pnpm [options] [run] <script>` where `<script>` is `test` or starts with `test:`, or `vitest` in any form) and does not begin, after environment assignments, with `timeout <duration>` | `timeout 600 pnpm test`, `FOO=1 timeout 60 pnpm --filter @alidade/core test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` |
| `write-outside-repo` | a call to a write tool (`fs_write`, `write`, `str_replace`, `fs_append`, `delete_file`) whose `path` resolves outside the Repository root and outside `/tmp/`                                                              | a write to `tools/kiro-guard/src/a.ts`                                                                                           |

4. FOR the `notes-private` rule, THE Guard SHALL examine, for every tool whatever its name, every string value of `tool_input` that is not under a Body key, including strings in arrays and nested objects, and, for a shell command, every Shell word. A string is a path of the Notes folder when, after `~` and `$HOME` or `${HOME}` at its start are replaced by `homeAbs`, a relative path is joined to the event's `cwd`, `.` and `..` segments and trailing slashes are removed, and the longest existing prefix is replaced by its real path, the result equals `<repository root>/notes` or begins with `<repository root>/notes/`. FOR ALL ways of writing one such path (prefix `./`, `..` detours, doubled slashes, trailing slash, absolute, `~`) the Decision SHALL be `refuse`.
5. THE Guard SHALL find a shell segment's command through: `VAR=value` assignments, the prefixes `env`, `sudo`, `command`, `nice`, `nohup`, `time` and `xargs`, the argument of `bash -c`, `sh -c` and `zsh -c`, command substitutions `$( … )` and back-quotes, and quotes. FOR ALL commands refused by criterion 3, wrapping them in `cd x && …`, `…; true`, `true || …`, `… | cat`, `bash -c '…'`, `sudo …`, or `echo $( … )` SHALL leave them refused, and wrapping an allowed command in the same ways SHALL leave it allowed.
6. THE Guard SHALL state its limits in its README and in a test that records them as examples: a command built from variables, globs, `eval`, an encoding or a script file is not understood and is allowed; the Guard's README says in one sentence that it is a guard against mistakes and not a security boundary, and the agent's `permissions` rules (Requirement 2) are the second line for `notes/`.
7. WHEN `context.only` is given, THE Guard SHALL apply only the rules it lists; `pre-tool-use --only notes-private` SHALL set it.

### Requirement 2: The project agent

**User Story:** As someone who opens the repository in Kiro CLI or the IDE, I want an agent that already knows the steering, the allowed tools and the guarded commands, so that I do not have to configure anything.

#### Acceptance Criteria

1. THE file `.kiro/agents/alidade.json` SHALL be valid JSON, and `kiro-cli agent validate --path .kiro/agents/alidade.json` SHALL exit `0`, and `kiro-cli agent upgrade --dry-run` on a copy of the folder SHALL report `0 errors`. _Since `validate` accepts an unknown trigger name and an unknown rule effect (checked on kiro-cli 3.5.0, design §3), criteria 2 to 6 are also checked by a test that does not depend on `validate`._
2. THE agent SHALL have `name` `alidade`, a `description`, an inline `prompt` of at most 12 lines that states the five rules a prompt can carry (units and sign conventions are in the steering; `pnpm` only; `notes/` is private and never read; no commit; every test run under `timeout`), `tools` equal to `["read", "write", "shell", "@alidade"]`, and `includeMcpJson` `true`.
3. ITS `resources` SHALL be exactly the five files `.kiro/steering/{math-conventions,product,structure,tech,testing}.md` as `file://` URIs, and each SHALL exist.
4. ITS rules SHALL be written in both forms that kiro-cli 3.5.0 loads (`toolsSettings` for the 2.x engine and `permissions.rules` for V3), with the same content: `fs_write` allowed for `./**`; `fs_read` and `fs_write` denied for `notes/**`; `shell` denied for `git commit *`, `git push *`, `pkill *`; no `allow` rule outside these. A test SHALL check that the two forms agree.
5. ITS `hooks` SHALL be an array of exactly three hooks, with the PascalCase triggers of the current documentation: `SessionStart` running `session-start`, `PreToolUse` with matcher `*` running `pre-tool-use`, `Stop` running `stop`, each as `node tools/kiro-guard/src/main.ts <subcommand>` with `timeout` at most `10` seconds. A test SHALL check that every trigger is in the documented set, every `effect` is `allow`, `ask` or `deny`, every `capability` is in the documented list, every `file://` and hook script exists, and that the string `notes` appears only in the deny rules and the prompt.
6. THE prompt, the resources and the hooks SHALL name no absolute path and no user name.

### Requirement 3: The repository's state at the start of a session and the reminder at the end

**User Story:** As the lead, I want the agent to start knowing the branch, what is uncommitted and the last commit, and to be told about the root checks when it changed code, so that it does not report done on unchecked work.

#### Acceptance Criteria

1. THE command `session-start` SHALL print to standard output, and exit `0`, at most 1 500 characters: the branch name (or `detached at <hash>`), the number of uncommitted paths and the first 15 of them with their status letters, `… and N more` for the rest, and the subject of the last commit with its short hash. IT SHALL leave out every path under `notes/`. IT SHALL run `git` through `execFileSync` with an argument array, in the Repository root, without a shell, and no other program.
2. WHEN the folder is not a git repository or `git` fails, `session-start` SHALL print one line saying so and exit `0`.
3. THE command `stop` SHALL print, WHEN at least one uncommitted path is under `skeleton/` or `apps/`, a reminder naming the changed packages and the four root checks in order: `timeout 900 pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check`; and SHALL print nothing otherwise. IT SHALL exit `0` in every case and SHALL NOT ask the session to continue.
4. FOR a temporary git repository built in the test, with a branch, a commit, and uncommitted files in each of `skeleton/`, `apps/`, `docs/` and `notes/`, the outputs SHALL be checked as exact strings, and the name of the `notes/` file SHALL NOT appear in either.

### Requirement 4: Three IDE hooks

**User Story:** As someone who opens the repository in the Kiro IDE, I want the math tests to run when I save a math file, the format of a requirements file to be checked when I save it, and the private notes to stay private, so that I find the mistake while I am still in the file.

#### Acceptance Criteria

1. THE folder `.kiro/hooks/` SHALL hold exactly three files, each with `"version": "v1"` and one hook, in the schema of the Kiro hooks documentation (`version`, `hooks[].name`, `trigger`, `matcher`, `action.type`, `action.command`, `timeout`): `math-tests-on-save.json` (trigger `PostFileSave`, matcher `(^|/)(apps|skeleton)/[^/]+/src/math/.+\.ts$`, command `math-tests`, `timeout` 330), `spec-format-on-save.json` (trigger `PostFileSave`, matcher `(^|/)\.kiro/specs/[^/]+/requirements\.md$`, command `check-spec`, `timeout` 10) and `notes-private.json` (trigger `PreToolUse`, matcher `*`, command `pre-tool-use --only notes-private`, `timeout` 10). A test SHALL check each field against the documented schema and each regular expression against example paths, relative and absolute.
2. THE command `math-tests` SHALL read the hook event, take every string of it that ends in `.ts` (the field that carries the saved path is not named in the documentation), keep those under `apps/*/src/math/` or `skeleton/*/src/math/` of the Repository root, and for each package run `timeout 300 pnpm --filter <package name> exec vitest run <test files>`, where the test files are the saved file if it is a `*.test.ts`, otherwise its `*.test.ts` and `*.property.test.ts` siblings that exist. WHEN the event names no such file, it SHALL use the changed files of `git status --porcelain` instead. IT SHALL exit `0` and print the counts when the tests pass, exit `1` and print the last 40 lines of the output when they fail, and exit `0` with one line when no test file exists.
3. THE command `check-spec <path>` (or the path from the event) SHALL check a `requirements.md` against the format of the existing specifications and list every problem with its line: the first line is `# Requirements Document`; the sections `## Introduction`, `## Glossary` and `## Requirements` exist in this order; the headings `### Requirement N: <title>` are numbered `1, 2, …` without a gap; each has a `**User Story:**` line and a `#### Acceptance Criteria` heading followed by at least one item numbered from `1.`; no number repeats. IT SHALL exit `0` for each of the five existing specifications' requirements files and for this one, and exit `1` listing the problems otherwise. A path outside `.kiro/specs/` or under `notes/` SHALL be refused with exit `1`.
4. THE hook `notes-private` SHALL be the same code as the agent's, limited to the one rule, so that a session in the IDE that does not use the `alidade` agent still cannot read the Notes folder.
5. SINCE the IDE cannot run on the machine that builds this, the Guard's README and the report SHALL say plainly that the hooks were checked against the documentation and not run in the IDE, and SHALL say how the schema was checked (design §6) and SHALL list what is not verified: that a save by the user, and not only by the agent, fires a `PostFileSave` hook; the name of the field that carries the path; the tool identifiers in `PreToolUse` events.

### Requirement 5: The MCP server speaks the protocol, by hand

**User Story:** As a developer, I want an MCP server of a few hundred lines that I can read in one sitting and that never fails on a bad message, so that the skeleton's tools are available to any MCP client without the SDK's web server stack.

#### Acceptance Criteria

1. THE package `tools/alidade-mcp` (`@alidade/mcp`) SHALL import only `@alidade/core`, `@alidade/sensors` and Node built-ins, SHALL add no external dependency, SHALL NOT import the MCP SDK, any web framework or any module that opens a socket, and its sources under `src/` (tests excepted) SHALL NOT reference `fetch`, `http`, `https`, `net`, `dgram`, `dns`, `fs`, `child_process` or `process.env`. A test SHALL scan for these names.
2. THE server SHALL read standard input as newline-delimited UTF-8 and write one JSON-RPC 2.0 message per line to standard output and nothing else there; it MAY write diagnostics to standard error. A line longer than 1 048 576 characters SHALL be discarded to its newline and answered with error `-32600` and `id` `null`. WHEN standard input closes, the server SHALL exit `0` after answering everything it read.
3. THE server SHALL answer these methods and no others: `initialize` (result with `protocolVersion`, `capabilities: { tools: {} }`, `serverInfo`, `instructions`; the version is the requested one when it is in `["2025-11-25", "2025-06-18"]`, otherwise `2025-11-25`), `ping` (result `{}`), `server/discover` (result with `resultType: "complete"`, `supportedVersions: ["2026-07-28", "2025-11-25", "2025-06-18"]`, `capabilities`, `_meta["io.modelcontextprotocol/serverInfo"]`, `instructions`), `tools/list` and `tools/call`. THE notifications `notifications/initialized` and `notifications/cancelled` SHALL be accepted and not answered; every other notification SHALL be ignored.
4. THE server SHALL be stateless: a request is answered the same before and after `initialize`. WHEN a request carries `params._meta["io.modelcontextprotocol/protocolVersion"]`, THE server SHALL serve it as version `2026-07-28` (its result has `resultType: "complete"`), or, if that version string is not in `supportedVersions`, answer error `-32022` with `data: { supported, requested }`. A request without it SHALL be served as a legacy one (its result has no `resultType`).
5. THE server SHALL answer these protocol errors, with `id` from the request where it has a usable one and `null` where it has not: invalid JSON `-32700`; a value that is not an object, a batch (an array), a missing or different `jsonrpc`, a missing or non-string `method`, or an `id` that is not a string, a number or `null` `-32600`; an unknown method `-32601`; `params` present and not an object, a `tools/call` without a string `name` or with `arguments` present and not an object, and an unknown tool name `-32602`. A request that is a notification (no `id`) SHALL never be answered, even with an error.
6. A tool whose arguments fail its checks, or whose computation fails, SHALL be answered with a result (not an error) with `isError: true` and one `text` content item that holds the Tool outcome as JSON. A tool that succeeds SHALL be answered with `isError: false`, the same JSON in one `text` item and in `structuredContent`.
7. FOR ALL byte strings written to standard input, whether or not they are valid UTF-8 or JSON, the server SHALL answer every line with exactly one line (or none for a notification), SHALL NOT exit and SHALL NOT write a line that is not valid JSON (a property test through the line handler, at least 200 cases, with generators for valid messages, mutated valid messages and random bytes).
8. THE integration test SHALL build the server in its setup into a temporary folder, start that file with `node` as a child process, send `initialize`, `notifications/initialized`, `tools/list`, one `tools/call` for each tool, `ping`, `server/discover`, an unknown method and a line of invalid JSON, read the answers from its standard output, check each against Requirements 5.3 to 5.6 and 6, close standard input and check that the process exits with code `0` within 5 seconds.

### Requirement 6: Three tools over the skeleton, registered for the workspace

**User Story:** As an agent or a developer, I want to compute a fix, a declination and a local offset with the skeleton's own functions from within a Kiro session, so that I check a number against the real code and not against my memory of it.

#### Acceptance Criteria

1. THE tool `fix_from_bearings` SHALL take `{ bearings: [{ id, observer: { latDeg, lonDeg }, positionAccuracyM, timeUtcMs, azimuthDeg, azimuthSigmaDeg }], outlierRejection?: boolean }` with 2 to 64 bearings, `azimuthDeg` being clockwise from **true** north, validate each through Core's `parseBearing`, solve with Core's `solve` and `BearingModel`, and return `{ ok: true, position: { latDeg, lonDeg }, covarianceEnM2: { varEastM2, varNorthM2, covEastNorthM2 }, ellipse1Sigma: { semiMajorM, semiMinorM, azimuthDeg }, ellipse95: { … }, ellipse95Scale, warnings, excludedIds, residuals: [{ id, residualDeg, normalisedResidual, studentisedResidual }], iterations }`, the 95 % ellipse and its scale coming from Core's `ellipse95` and `CONFIDENCE_95_SCALE`, never from a copy. A fix SHALL never be returned without both ellipses (`product.md`, principle 1).
2. THE tool `magnetic_declination` SHALL take `{ latDeg, lonDeg, timeUtcMs }` and return `{ ok: true, declinationDeg, sigmaDeg, positiveEast: true }` from Sensors' `declinationAt`.
3. THE tool `local_offset` SHALL take `{ direction: "to_offset", origin, position }` (both `{ latDeg, lonDeg }`) and return `{ ok: true, eastM, northM }` from Core's `projectToLocalPlane`, or `{ direction: "to_position", origin, eastM, northM }` (each offset within ±20 015 087 m, half the circumference of the sphere: beyond it Core wraps the offset around the sphere and returns a finite but meaningless position, found by the hostile-input test) and return `{ ok: true, position }` from Core's `unprojectToLocalPlane`.
4. EVERY name SHALL carry its unit suffix, degrees appearing only at this boundary; the conversion SHALL use Core's `degToRad` and `radToDeg`; no formula of the skeleton SHALL be repeated.
5. EVERY argument SHALL be checked before any computation: the type of each field, finite numbers only, strings of 1 to 128 characters for ids, at most 64 bearings, no unknown field (reason `invalid_arguments`, naming the field in `field`). A failure SHALL be `{ ok: false, reason, message, field?, id? }`, where `reason` is Core's `Reason`, Sensors' `SensorReason` or `invalid_arguments`, and `message` is plain words from a table typed `Record<Reason, string>` (and one for Sensors' extra reasons), with no code, no underscore and no `NaN`. A completeness test SHALL fail when a reason has no message.
6. NO number in a Tool outcome, a result or an error SHALL be `NaN` or infinite; a handler whose computation would produce one SHALL return `{ ok: false, reason: 'non_finite_result' }`. FOR ALL Hostile inputs, each handler SHALL return without throwing and every number reachable in its outcome SHALL be finite (property tests, at least 200 cases each, generators that state their domain, and an example for each degenerate case a generator excludes).
7. THE tools SHALL be checked against Core's and Sensors' own results: for synthetic bearings built with Core's `initialAzimuthRad` from a known target, the returned position SHALL be within 1 m of the target; `magnetic_declination` SHALL equal `declinationAt` converted with `radToDeg`; `local_offset` in both directions SHALL round-trip within `1e-6 m`.
8. THE file `.kiro/settings/mcp.json` SHALL register the server `alidade` with `command` `node`, `args` `["tools/alidade-mcp/dist/server.mjs"]` and `autoApprove` of the three tool names (they read nothing and write nothing), and no `env`. THE README of the package SHALL say that it speaks MCP versions `2026-07-28`, `2025-11-25` and `2025-06-18`, that it must be built once with `pnpm --filter @alidade/mcp build` (`dist/server.mjs` is not committed, and the server never builds anything itself), and how to see it in Kiro (`/mcp` in the CLI, the MCP Servers view in the IDE), and show one worked example: a synthetic fire seen from two synthetic posts, with the two requests and the answers. A test SHALL extract the example's requests from the README, run them through the line handler and compare the answers to the README's, so that the example cannot go stale.
